## Key Question 1: tuicr — what it is, stack, features, maturity

### Takeaway
tuicr (github.com/agavra/tuicr) is a Rust/ratatui, MIT-licensed, single-binary "GitHub-style PR review in the terminal" tool created January 2026 that is strong on comment capture, forge push (GitHub/GitLab/Gitea/Bitbucket/Azure DevOps/Gerrit), persisted review state, and an agent-facing JSON `review` CLI, but has **no AI features, no LSP, and no stack awareness**; PR review is API/diff-based with no checkout or clone.

### Inferences
- tuicr's "sessions as JSON files + `active_sessions.json` + CLI" design is a de facto protocol for agent/TUI collaboration that a new tool could adopt or interoperate with (slug formats `gh:owner/repo/pr/N`, `owner/repo@branch/worktree`).
- Because PR review is API-driven with no checkout, tuicr cannot offer "ask AI with repo context", semantic navigation, or full-stack diffs; these are the gaps a new tool could exploit.
- Star growth (0 to 3.4K in ~9 months) and weekly releases suggest a healthy single-maintainer project (author "agavra"), but the open-issue count (92) and the forge-reply/commit-attribution gaps show room for a stack-aware competitor.

### Gaps
- Exact session JSON schema fields beyond those listed (I read `--help` and docs, not `model/` structs in full).
- No HN/Reddit reception data found; adoption evidence is limited to stars and Homebrew analytics.

## Key Question 2: plannotator — stack, PR review mode, guided review, Ask AI, BYOK, state, export, licensing, maturity

### Takeaway
Plannotator (github.com/backnotprop/plannotator) is a TypeScript/Bun + React, dual MIT/Apache-2.0, **browser-based local review surface** (with a separate Rust/ratatui `plannotator-tui` for Markdown only) at 9.6K stars; its PR mode pulls GitHub/GitLab PRs into a detached `git worktree` (same repo) or a `gh/glab repo clone --depth=1 --no-checkout` temp clone, infers stacks from PR base branches via GitHub GraphQL, and its Guided Review is a schema-constrained JSON (`title/intent/sections[{title,overview,diffs[{file,summary}]}]/unplacedFiles`) produced by the user's **already-authenticated agent CLI** (Claude Code, Codex, Cursor, OpenCode, Pi, Copilot) rather than by API keys; there is no BYOK API-key path and no LSP (code navigation is ripgrep-based).

**PR review mode**
- Docs: pass a GitHub PR or GitLab MR URL to `/plannotator-review` or `plannotator review <url>`; requires authenticated `gh` or `glab` (`--hostname` for enterprise). "Plannotator loads the provider diff so the browser opens quickly. It then prepares a local checkout in the background." "If the current repo matches the URL's host, owner, and repo, Plannotator fetches the review head into a detached Git worktree. Otherwise, it uses the provider CLI to create a shallow temporary clone. The checkout is deleted when the review session ends." `--no-local` skips the checkout (diff-only; no Ask AI, agent reviews, Code Tours, Guided Reviews, code navigation, semantic diff, full-stack comparison). [docs] — [pull-requests.md](https://docs.plannotator.ai/open-source/workflows/pull-requests.md)
- Source confirms: `getPRHeadFetchSpec` returns `refs/pull/<N>/head` (GitHub) or `refs/merge-requests/<iid>/head` (GitLab); `getPRCloneCommand` runs `gh repo clone owner/repo <dest> -- --depth=1 --no-checkout` (or `glab`), setting `GH_HOST`/`GITLAB_HOST` for non-default hosts; Bitbucket uses plain `git clone --depth=1 --no-checkout` with `GIT_TERMINAL_PROMPT=0`. `packages/shared/worktree.ts` runs `git worktree add [--detach] <path> <ref>` and `git worktree remove [--force]`. [source-verified] — [pr-types.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-types.ts); [worktree.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/worktree.ts)
- Stack detection (PR mode): `getPRStackInfo` marks a PR as stacked when `metadata.baseBranch !== metadata.defaultBranch` (`source: "branch-inferred"`); `fetchGhPRStack` walks up (`baseRefName` chain to default branch) and down (`headRefName` to leaf PRs) with GitHub GraphQL `pullRequests(headRefName:/baseRefName:, states:[OPEN, MERGED])` to build a `PRStackTree { nodes: PRStackNode[{branch, number, title, url, isCurrent, isDefaultBranch, state}] }`. `PRStackInfo.source` union also reserves `"github-native" | "gitlab-native" | "graphite" | "ghstack"` but only `branch-inferred` and `tree-discovered` are produced in source (no Graphite/ghstack parsing found). Diff scopes: "Layer" (`origin/<base>...HEAD`) vs "Full stack" (`origin/<default>...HEAD`, requires local checkout). Docs: GitHub shows a PR stack tree with in-UI PR switching; GitLab identifies stacked MRs but has no tree/switcher; "Before posting inline comments, return to Layer." [source-verified + docs] — [pr-stack.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-stack.ts); [pr-github.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-github.ts)
- Local stack detection (not PR): an internal evaluation ADR (2026-07-03) tested a "merge-base reachability" heuristic (parent P qualifies iff `merge-base(B,P)` is not an ancestor of default D; pick deepest merge-base). It passed clean-stack cases but has a "dangerous" child-branch trap (a branch cut from B wins and silently hides B's own commits), which is "provably undetectable by graph queries alone"; reflogs record only `branch: Created from HEAD`. Determination: if built, "Suggest, never auto-apply", persist the user's explicit base choice per repo+branch as a ref name, show all qualifiers; once a PR exists the platform-declared base should supersede. Status: "evaluation only. Decision pending." [source-verified] — [adr/eval-local-stack-detection-20260703.md](https://github.com/backnotprop/plannotator/blob/main/adr/eval-local-stack-detection-20260703.md)
- Local review modes (v0.22.0 notes): "All changes" default = merge-base with base branch vs working tree incl. untracked; git status panel (Committed/Changes/Untracked, per-row viewed tracking, stage/unstage); base-drift banner with one-click fetch; Commits panel with per-commit diffs that can be annotated, annotations anchored to the commit. Docs also list GitButler, Jujutsu, and Perforce workspace detection (`gitbutler-core.ts` in source). [docs; GitButler source-verified] — [v0.22.0 notes](https://newreleases.io/project/github/backnotprop/plannotator/release/v0.22.0); [code-review docs](https://docs.plannotator.ai/code-review)

**Review state, code navigation, export**
- Viewed state: GitHub per-file viewed state is fetched (GraphQL) at open and synced back (`markPRFilesViewed`); docs: "GitHub can also sync each file's viewed state with the PR." Locally there is an auto-mark-viewed heuristic (`autoViewed.ts`) and a "hide viewed files" toggle; guide sections carry their own reviewed booleans. [source-verified] — [pr-github.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-github.ts)
- Code navigation is **search-based, not LSP**: `packages/shared/code-nav.ts` header "Search-based code navigation"; it shells out to `rg` and returns `CodeNavLocation { kind: "definition"|"reference", confidence: "likely"|"possible", filePath, line, column, snippet }` with `backend: "search" | "unavailable"`. [source-verified] — [code-nav.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/code-nav.ts)
- Export destinations: "Agent" (structured feedback returned to the coding agent/terminal; not posted to provider) or "GitHub"/"GitLab" (review comments or approval via `gh`/`glab`; inline comments must map to the current provider diff; GitLab posts general note, inline discussions, approval via separate APIs with partial-failure retry). Agent-review findings are never auto-posted. External tools can POST findings onto a diff via an HTTP API (marketing claim). [docs] — [pull-requests.md](https://docs.plannotator.ai/open-source/workflows/pull-requests.md); [plannotator.ai/code-review](https://plannotator.ai/code-review/)

### Inferences
- Plannotator's guide schema is deliberately minimal (file-level refs, no hunk ranges) and relies on server-side coverage validation; a tool wanting hunk-level narration would need to extend to ranges (which Plannotator's spec once had and dropped) or borrow the Code Tour anchor model.
- Its reliance on agent CLIs for AI means zero credential handling but a hard dependency on those CLIs being installed and logged in; a BYOK-API-key approach would be a differentiator for users without those subscriptions.
- The GitHub GraphQL base/head walk is a simple, reusable stack-discovery technique that needs no Graphite/ghstack metadata.

### Gaps
- The exact "Send feedback" markdown payload for code review (I only verified plan/annotate templates in `feedback-templates.ts`).
- The precise local on-disk location/format of non-guide review state (annotations/viewed) was not located beyond `PLANNOTATOR_DATA_DIR`.
- No independent (HN/Reddit) reception data found.

## Key Question 3: Closest peers and feature matrix

### Takeaway
Among ~15 peers, none combines human inline comments on local ranges with an AI chunked walkthrough and BYOK/credential reuse, and **none documents LSP/jump-to-definition**; the nearest peers to a tuicr/plannotator hybrid are lumen (Rust TUI, own-API-key AI explain, GitHub-synced viewed state), difit (local web, copy-as-prompt export), hunk (OpenTUI, agent-authored annotations only) and revdiff (Go TUI, stdout export + Claude Code/Codex plugins). Findings in this section were gathered by a delegated researcher from READMEs/docs; items marked "unverified" were not confirmed against primary sources.

### Cited Findings
Feature key: (a) local branch/range review with inline comments; (b) pull a GitHub PR locally; (c) AI chunked walkthrough; (d) ask AI; (e) BYOK / reuse of Claude Code or Codex credentials; (f) mark files/hunks reviewed, persisted; (g) LSP/jump-to-def; (h) export comments to agent and/or post to GitHub.

- **hunk** (modem-dev/hunk): "Review-first terminal diff viewer for agentic coders", TypeScript on OpenTUI + Pierre diffs, MIT; `hunk diff/show/log` (`v` in `hunk log` selects a commit range), `hunk gh compare main...feature` and `hunk gh` open PRs "without the GitHub CLI" using `GH_TOKEN`/`GITHUB_TOKEN`; annotations are agent-authored ("inline AI and agent annotations beside the code", fed by a `hunk-review` skill / `--agent-context`), no human comment authoring, no API keys, no LSP; auto-detects jj and Sapling; persistent `state.json` contents undocumented. ## Key Question 4: How stack-aware tools represent stacks locally and on GitHub

### Takeaway
No two tools share a metadata format, but nearly all of them chain GitHub PR `base` branches to the parent PR's head branch, so walking PR bases (as plannotator does via GraphQL) is the universal fallback; locally, ghstack/spr/jj expose parseable branch-name conventions, Graphite/git-town/git-stack store parent links in git config or object-DB refs, and getcord/spr and ghstack add commit trailers.

### Cited Findings
- **ghstack**: per commit three branches `gh/<user>/<N>/base` ("never force-pushed"), `gh/<user>/<N>/head` ("We open a pull request on this branch, requesting to merge into base"), `gh/<user>/<N>/orig`; PR base is the `/base` branch, not main. Trailers `ghstack-source-id: <sha>` and `Pull Request resolved: <url>` and PR-body "Stack from [ghstack]" list with `* __->__ #N` marker are widely known but **unverified this session** (source fetch 404'd); Sapling's ReviewStack "recognizes stacks created by `sl pr submit`, `sl ghstack`, or standalone `ghstack`". — [ghstack](https://github.com/ezyang/ghstack); [ReviewStack](https://sapling-scm.com/docs/addons/reviewstack/)
- **ejoffe/spr**: config `branchPrefix` default `spr`, `githubBranch` target, `prTemplateType` default `stack`, `showPrTitlesInStack` ("Show PR titles in stack description within PR body"); commit subject = PR title, body = description; `git spr merge` merges in order. `commit-id:` trailer and `spr/<target>/<id>` pattern **unverified**. — [ejoffe/spr](https://github.com/ejoffe/spr)
- **getcord/spr**: spr 1.x wrote `Pull Request:`; spr 2.0 writes trailers `Pull-request:`, `Reviewers:`, `Reviewed-by:`; `spr diff --all` creates one PR per commit "stacked on top of each other". Branch names `spr/<user>/<slug>` and synthetic `spr/main/<hash>` bases **unverified**. — [getcord/spr](https://github.com/getcord/spr)
- **Graphite (gt)**: repo config `.git/.graphite_repo_config`; branch metadata stored as JSON blobs in the git object DB via `git hash-object` + `git update-ref` ("small JSON blobs keyed on branch names" mapping branch to parent); ref namespace `refs/branch-metadata/<branch>` with `parentBranchName`/`parentBranchRevision` is third-party/unverified. On GitHub each PR's base is its parent branch and the PR body carries "This stack of pull requests is managed by Graphite". — [Graphite init](https://graphite.dev/docs/initialize-in-a-repo); [Graphite blog](https://graphite.com/blog/git-key-value); [example PR](https://github.com/rivet-dev/rivet/pull/3511); [intro](https://graphite.com/docs/intro-to-graphite.md)
- **Aviator av**: Go, ~510 stars; "av internally keeps tracks of the PRs, their associated branches and their dependent branches"; remembers each branch's base commit; `av pr` "automatically sets the base branch in GitHub as `bookstore-backend` rather than `main`". Storage path (`.git/av/av.db`) and PR-body text unverified. — [av](https://github.com/aviator-co/av); [docs](https://docs.aviator.co/aviator-cli)
- **jj**: bookmarks are "named pointers to revisions (just like branches are in Git)", remote bookmarks `<bookmark>@<remote>`; `jj git push --change` "generates bookmark names with a prefix of "push-"", configurable via `templates.git_push_bookmark` (e.g. `"martinvonz/push-" ++ change_id.short()`). No PR-body/trailer convention. — [jj bookmarks](http://docs.jj-vcs.dev/latest/bookmarks/); [jj config](https://docs.jj-vcs.dev/latest/config/)
- **git-branchless**: event log "stored on disk in a SQLite database"; refs under the `refs/branchless` prefix; no GitHub PR representation. Exact `.git/branchless/db.sqlite3` path unverified. — [Architecture wiki](https://github.com/arxanas/git-branchless/wiki/Architecture); [git list](https://lore.kernel.ime.usp.br/git/xmqqil581jq4.fsf@gitster.g/t/)
- **git-stack (gitext-rs)**: no metadata refs; stacks inferred from git config (`stack.protected-branch`, `stack.protect-commit-age/-count`, `stack.auto-base-commit-count`, `stack.push-remote`). — [reference](https://github.com/gitext-rs/git-stack/blob/main/docs/reference.md)
- **git-town**: lineage in git config, documented as `git-town.<branch>.parent` in prose and `git-town-branch.<branch>.parent` in examples (older versions also `ancestors`); `git town propose --stack` creates proposals for all branches. Current key prefix unverified; check `git config --get-regexp 'git-town.*parent'`. — [branch_hierarchy v7.3](https://github.com/Originate/git-town/blob/v7.3.0/documentation/development/branch_hierarchy.md); [propose](https://www.git-town.com/commands/propose)
- **GitButler**: single `gitbutler/workspace` branch whose merge commit is rebuilt; applied branches under `refs/gitbutler/<branch>`; plannotator detects it via HEAD at the workspace ref and `gitbutler.project.targetref`. On GitHub: native stacked PRs when available, else "GitButler-managed stack information in their descriptions"; bottom PR targets main, each PR above targets the nearest lower branch with a PR. — [workspace branch](https://docs.gitbutler.com/workspace-branch); [stacked branches](https://docs.gitbutler.com/features/stacked-branches); [plannotator GitButler docs](https://docs.plannotator.ai/open-source/workflows/gitbutler)
- **Sapling / ReviewStack**: `sl pr submit` "appends a footer to each pull request body with a link to the stack on reviewstack.dev" (template `pull-request-review-url-template`; disable with `github.pull-request-include-reviewstack=false`); internal branch `sapling-pr-archive-<user>`. PR-body `* #N` / `__->__` list unverified. — [ReviewStack](https://sapling-scm.com/docs/addons/reviewstack/); [Sapling GitHub](https://sapling-scm.com/docs/git/github/)
- **Plannotator's own approach** (see Q2): PR stacks inferred purely from GitHub PR `baseRefName`/`headRefName` chains via GraphQL, `isStacked = baseBranch !== defaultBranch`; local stack parent detection evaluated with a merge-base heuristic and deferred because of the undetectable child-branch trap. — [pr-stack.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-stack.ts); [ADR](https://github.com/backnotprop/plannotator/blob/main/adr/eval-local-stack-detection-20260703.md)

### Inferences
- Parse hints for a reviewer tool: branch names `gh/<user>/<N>/{head,base,orig}`, `spr/*`, `push-<changeid>`, `gitbutler/workspace` + `refs/gitbutler/*`, `sapling-pr-archive-*`; trailers `Pull-request:`/`Pull Request:`, `ghstack-source-id:`, `Pull Request resolved:`, `commit-id:`; config/refs `.git/.graphite_repo_config` + object-DB JSON, `git-town[-branch].<b>.parent`, `stack.*`, `refs/branchless/*`, `gitbutler.project.targetref`; PR body markers "managed by Graphite", reviewstack.dev footer, GitButler stack info, `__->__`.
- The most robust cross-tool strategy is the one plannotator ships: treat the forge's declared PR base chain as truth when a PR exists, and only *suggest* a local parent from merge-base analysis, persisting the user's explicit choice per branch.

### Gaps
- Exact on-disk formats for Graphite refs, av's database, git-branchless's SQLite path, and the ghstack/spr trailer strings were not confirmed from primary sources this session.
