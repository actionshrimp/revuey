## Key Question 1: Rendering mixed documents (prose + highlighted multi-language code excerpts + diff coloring + LSP inside excerpts)

### Takeaway
Neovim can render a "guided review" document natively: markdown fenced blocks already get per-language tree-sitter injection highlighting out of the box in 0.12 (markdown parser is bundled and highlighting is enabled by default), and extmarks (line/range highlights at a priority above tree-sitter, `virt_lines`, `conceal_lines`, signs) layer +/- diff coloring on top without disturbing the injected syntax. The hard limit is LSP: built-in LSP attaches to a *buffer* with a real file URI and filetype, so jump-to-definition/hover from inside an excerpt embedded in a prose buffer is not something the LSP client provides; the realistic pattern is "excerpt is a portal": a keymap on the excerpt jumps to the real file buffer (in the worktree) at the mapped line and runs `vim.lsp.buf.definition()`/`hover()` there.

### Cited Findings
Tree-sitter injections and the bundled markdown pipeline
- Neovim 0.12 bundles parsers for `c, lua, markdown, markdown_inline, query, vim, vimdoc` (local 0.12.4 runtime: `$VIMRUNTIME/parser/`), and 0.12 "Enabled treesitter highlighting for Markdown files" by default — [`:help news`](https://neovim.io/doc/user/news.html) (local 0.12.4 runtime help).
- The shipped markdown injection query injects fenced blocks by the info-string language: `(fenced_code_block (info_string (language) @injection.language) (code_fence_content) @injection.content)` — [runtime/queries/markdown/injections.scm](https://github.com/neovim/neovim/blob/master/runtime/queries/markdown/injections.scm) (verified identical in local 0.12.4 runtime).
- Injection queries support `@injection.language`, `@injection.content`, and notably `@injection.filename` — "the corresponding filetype is then looked-up up via `vim.filetype.match()` and treated as the name of a language" — plus properties `injection.combined`, `injection.include-children`, `injection.self`, `injection.parent`. Caveat: "Injection queries are currently run over the entire buffer, which can be slow for large buffers." — [`:help treesitter-language-injections`](https://neovim.io/doc/user/treesitter.html#treesitter-language-injections) (local 0.12.4 runtime help).
- `vim.treesitter.query.get()`/`parse()` have "Strong treesitter-query caching" since 0.11, and 0.11 "Significantly reduced redraw time for long lines with treesitter" — [`:help news-0.11`](https://neovim.io/doc/user/news-0.11.html) (local 0.12.4 runtime help).
- nvim-orgmode (requires "Neovim 0.12.0 or later") highlights `#+BEGIN_SRC filetype` blocks through its own injection query (`queries/org/injections.scm`), which captures the block parameter as `@_lang` and the contents as `@injection.content` and sets the language with a custom `#org-set-block-language!` directive; inline `src_lang{...}` blocks and LaTeX envs are handled the same way with `injection.include-children` — [nvim-orgmode README](https://github.com/nvim-orgmode/orgmode); [orgmode injections.scm](https://raw.githubusercontent.com/nvim-orgmode/orgmode/master/queries/org/injections.scm). The README lists "Highlighted code blocks" as a feature but does not mention org-babel execution — [nvim-orgmode README](https://github.com/nvim-orgmode/orgmode).

Extmarks as the overlay layer
- `nvim_buf_set_extmark` supports: `virt_lines` ("an array over lines, where each line in turn is an array over `[text, highlight]` tuples"; "'wrap' and 'linebreak' options do not take effect"), `virt_lines_above`, `virt_lines_leftcol`, `virt_lines_overflow = "scroll"` (0.11+), `virt_text_pos = "inline"` (shifts buffer text right), `conceal_lines` ("lines in the range are not drawn at all", 0.11+), `hl_group` with `end_row`/`end_col`, `line_hl_group`, `sign_text`, `url` (OSC 8 hyperlinks in the TUI), `priority`, `undo_restore`, `invalidate` — [`:help nvim_buf_set_extmark()`](https://neovim.io/doc/user/api.html#nvim_buf_set_extmark()) (local 0.12.4 runtime help); `conceal_lines` and `virt_lines_overflow=scroll` were added in 0.11 — [`:help news-0.11`](https://neovim.io/doc/user/news-0.11.html).
- Highlight layering is deterministic: `vim.hl.priorities` = syntax 50, treesitter 100, semantic_tokens 125, diagnostics 150, user 200 — [`:help vim.hl.priorities`](https://neovim.io/doc/user/lua.html#vim.hl.priorities) (local 0.12.4 runtime help). A plugin extmark with a background-only `DiffAdd`-style group at priority >100 therefore stacks a +/- background under the injected foreground syntax colors.
- render-markdown.nvim (5,181 stars, pushed 2026-10-10 — GitHub API) is the reference implementation of "prose buffer + decorated code blocks": it renders code-block "background, language icon, name, and info", draws thin borders with `▄`/`▀` characters, offers `anti_conceal` ("hiding added text on the line the cursor is on"), updates only "within the context of the visible window, not the entire buffer", can disable above `max_file_size`, is "File type agnostic: can render `markdown` injected into any file", has an `injections` table (ships a gitcommit example query), `custom_handlers` keyed by tree-sitter language, and `overrides` by `buftype`/`filetype`/preview; minimum Neovim ">= 0.9.0", ">= 0.10.0" recommended; rendered windows use conceallevel 3 — [render-markdown.nvim README](https://github.com/MeanderingProgrammer/render-markdown.nvim).
- markview.nvim (3,667 stars, pushed 2026-10-18 — GitHub API) is the main alternative; a Neovim Discourse comparison calls the two "neck-to-neck in terms of feature sets", and render-markdown's docs list markview among plugins that "will likely clash" if run together — [neovim.discourse.group](https://neovim.discourse.group/t/how-would-you-compare-render-markdown-nvim-to-markview-nvim/5176); [markview README](https://github.com/OXY2DEV/markview.nvim).
- Why extmarks rather than `:syn-conceal`: org-bullets.nvim's rationale is that "conceal can only have one global highlight and conceal doesn't work when a block is folded" — [org-bullets README](https://github.com/nvim-orgmode/org-bullets.nvim).

Diff coloring + syntax highlighting simultaneously (the three realistic approaches)
- (a) Native diff mode on two real buffers: 0.12 `'diffopt'` default is `"internal,filler,closeoff,indent-heuristic,inline:char,linematch:40"`; `inline:` "configures diff highlighting for changes within a line", new `hl-DiffTextAdd` "highlights added text within a changed line", and `'diffanchors'` "specifies addresses to anchor a diff" (also `anchor` in `'diffopt'`) — [`:help news`](https://neovim.io/doc/user/news.html); [`:help diff-anchors`](https://neovim.io/doc/user/diff.html#diff-anchors) (local 0.12.4 runtime help). Tree-sitter highlighting of each side continues to apply in diff mode; this is what diffview.nvim does (two windows + `diffthis`).
- (b) Compute hunks yourself with `vim.text.diff(a, b, opts)` (renamed from `vim.diff()` in 0.12: "`vim.diff()` Renamed to `vim.text.diff()`" — [`:help deprecated`](https://neovim.io/doc/user/deprecated.html)); options include `algorithm` (`myers|minimal|patience|histogram`), `ctxlen`, `interhunkctxlen`, `linematch`, `ignore_whitespace*`, `indent_heuristic`, and `result_type = 'unified' | 'indices'` or an `on_hunk` callback — [`:help vim.text.diff()`](https://neovim.io/doc/user/lua.html#vim.text.diff()) (local 0.12.4 runtime help). Then paint `line_hl_group`/`hl_group` extmarks and show removed lines as `virt_lines`. This is the unified/inline pattern used by mini.diff's overlay ("Deleted reference lines are shown as virtual text"), unified.nvim ("inline, unified diff viewer", gutter signs + `DiffAdd/DiffDelete/DiffChange`), codediff.nvim's inline layout ("single pane with virtual lines"), and diffview-plus's `diff1_inline` layout ("unified, via extmark overlays") — [mini.diff README](https://github.com/nvim-mini/mini.diff); [unified.nvim README](https://github.com/axkirillov/unified.nvim); [codediff.nvim README](https://github.com/esmuellert/codediff.nvim); [diffview-plus README](https://github.com/dlyongemallo/diffview.nvim).
- (c) Tree-sitter-highlight a *patch/diff-format buffer*: diffs.nvim ("Treesitter-powered Diff Syntax highlighting for Neovim", 202 stars, pushed 2026-10-11 — GitHub API) does exactly this for fugitive/Neogit/builtin `diff` filetype/gitsigns/fzf-lua: "Treesitter parses each diff hunk in isolation", uses a "decoration provider" that "applies highlights on the next redraw cycle", supports word/char-level highlighting "driven by 'diffopt' 'inline:'", and can use codediff.nvim's native library as a "vscode-diff algorithm FFI backend for word-level intra-line accuracy". Stated limitations: "Hunks that start or end mid-expression may highlight imperfectly", a per-language cold-start stutter, and conflicts with diffview.nvim/mini.diff/gitsigns/git-conflict — [diffs.nvim README](https://github.com/barrettruth/diffs.nvim).
- octo.nvim renders PR review-thread diff snippets inside its comment buffers as virtual-text boxes (`┌ │ └`) where "added lines are tinted with `DiffAdd` and removed lines with `DiffDelete`", i.e. a pure virt_text approach with no syntax highlighting of the snippet — [octo.nvim writers.lua](https://raw.githubusercontent.com/pwntester/octo.nvim/master/lua/octo/ui/writers.lua).

LSP inside an injected block
- LSP clients attach by buffer: `vim.lsp.Config.filetypes` is "Filetypes the client will attach to", `root_dir`/`root_markers` resolve "from the buffer file", and `vim.lsp.enable()` "Activates LSP for current and future buffers" — [`:help vim.lsp.Config`](https://neovim.io/doc/user/lsp.html#vim.lsp.Config) (local 0.12.4 runtime help). Nothing in `lsp.txt` offers a way to associate a sub-range of one buffer with a different file URI.
- nvim-treesitter (main branch) itself documents that highlighting is enabled per filetype "with `vim.treesitter.start()` in a `ftplugin` file or a `FileType` autocommand" — [nvim-treesitter README](https://github.com/nvim-treesitter/nvim-treesitter).

### Inferences
- Cleanest architecture for the guided-review document: a markdown (or custom-filetype) scratch buffer with fenced blocks whose info string names the language (or use `@injection.filename` with the real path so `vim.filetype.match()` picks the language, which also covers `.tsx`, `.vue`, etc.), plus one extmark namespace for `line_hl_group` DiffAdd/DiffDelete backgrounds and sign-column +/- markers, and `virt_lines` for removed lines if you prefer to keep only the "after" text as real buffer text. Because injected highlighting is priority 100 and your overlays can be >100 with background-only groups, "diff coloring + syntax highlighting simultaneously" falls out of the priority model with no special tricks.
- If the excerpt contains both `-` and `+` lines as real text, tree-sitter will parse the union (which is syntactically wrong code). Prefer the mini.diff/unified.nvim pattern: keep the *new* side as real text (parses cleanly, LSP-free navigation works), and inject removed lines as `virt_lines` highlighted with `DiffDelete` (they will not be syntax-highlighted; octo.nvim and mini.diff accept the same trade-off). Alternatively, render two injected blocks (old/new) per hunk.
- LSP "jump-to-definition from an excerpt" should be implemented as: store `{path, line}` mapping in extmarks (or a side table keyed by extmark id), and on `gd`/`K` open the real worktree file in a split/float at that line and call `vim.lsp.buf.definition()`/`hover()` there. A float with the real file buffer gives "hover-like" behavior without leaving the review document.
- render-markdown.nvim's `file_types`/`overrides` for `nofile` buffers and `custom_handlers` make it viable to reuse rather than rewrite the prose decoration layer, but it is optional: the built-in markdown highlighting + injections already provide language coloring; render-markdown adds polish (borders, headings, anti-conceal).
- nvim-orgmode proves that a custom tree-sitter grammar with custom injection directives works on 0.12, but adopting org as the document format is only attractive if the user already lives in org (the user does have orgmode + org-roam installed). Markdown is the lower-risk default because its parser is bundled with Neovim.

### Gaps
- I did not find a plugin that implements "LSP-aware code excerpt inside a prose buffer" (i.e. forwarding `textDocument/definition` from a sub-range to another file). I found no evidence the built-in client supports it; the portal approach is an inference.
- I could not fetch diffs.nvim's source to confirm whether its hunk-isolation uses `LanguageTree:set_included_regions` or separate parsers; the README only says a decoration provider is used.
- I did not measure performance of injection queries for a review document containing hundreds of fenced blocks; the help text only warns injections run over the whole buffer.

## Key Question 2: Existing plugins to reuse or learn from (status as of 2026-10-21)

### Takeaway
The ecosystem is healthy but fragmented: diffview is alive only as the `diffview-plus.nvim` fork (and a 0-star PR-review fork with per-branch "reviewed" state), octo.nvim and gitlab.nvim are the two mature "review with threads" implementations (both actively pushed in October 2026), codediff.nvim is the fast-moving newcomer with a native diff engine and PR mode, and diffs.nvim/mini.diff/gitsigns provide reusable rendering primitives. No existing plugin combines branch-stack diffs, chunk-level "reviewed" marks, inline comments, an AI guided-review document and LSP in one surface.

### Inferences
- Reuse candidates by layer: (1) diff rendering — fork/vendor diffview-plus for the two-window file-panel model, or build on `vim.text.diff` + extmarks following mini.diff/unified.nvim for a unified view (far less code; mini.diff is ~1 file); (2) tree-sitter highlighting of patch text — diffs.nvim's hunk-isolation technique; (3) GitHub plumbing — octo.nvim's `gh`-based fetching and thread model are the most battle-tested but are tied to octo's buffers; gh-review.nvim is small enough to read in an afternoon; (4) "reviewed" state — dimfeld's fork is the only prior art for blob-hash-keyed per-branch review marks and is worth copying conceptually.
- None of the plugins supports tree-sitter-less environments; all modern ones assume 0.10+, and the main-branch nvim-treesitter requires 0.12. Targeting Neovim ≥ 0.11 (for `vim.lsp.config`, `conceal_lines`) or ≥ 0.12 (for `vim.text.diff` naming, `vim.pack`, default markdown highlighting) is consistent with the ecosystem.
- Parser availability is the real fragility: beyond the 7 bundled parsers, TypeScript/TSX parsers must come from nvim-treesitter (main) or the user's own install; a review plugin should degrade gracefully (use `vim.treesitter.language.add()` returning `true` if loaded — [`:help news-0.11`](https://neovim.io/doc/user/news-0.11.html)) rather than fail.

## Key Question 3: LSP for files in a temporary worktree (TypeScript)

### Takeaway
Neovim 0.11+ `vim.lsp.config`/`vim.lsp.enable` resolves the root per buffer upward from the file via `root_markers`, so a worktree under e.g. `/tmp/review-xyz/` gets its own client instance keyed by `(name, root_dir)` automatically; the remaining problem is purely TypeScript's: tsserver resolves type information from `node_modules`, so a worktree without `node_modules` yields mass errors and broken go-to-definition into dependencies. Available mitigations are a package install in the worktree, a symlink to the main checkout's `node_modules`, or a `fallbackPath`/global TypeScript (which fixes the server starting but not dependency resolution).

### Cited Findings
- `vim.lsp.config()` and `vim.lsp.enable()` were added in 0.11 — [`:help news-0.11`](https://neovim.io/doc/user/news-0.11.html). In 0.12: `vim.lsp.ClientConfig` gained `workspace_required`, "You can control the priority of `vim.lsp.Config` `root_markers`", `vim.lsp.enable()` "start/stops clients as necessary", `:lsp` command for interactive management, `:checkhealth vim.lsp` — [`:help news`](https://neovim.io/doc/user/news.html) (local 0.12.4 runtime help).
- `root_markers`: "For each item, Nvim will search upwards (from the buffer file) for that marker … the directory is used as the root dir (workspace folder)"; `root_dir` may be a function `fun(bufnr, on_dir)` and "can dynamically decide per-buffer whether to activate (or skip) LSP"; `reuse_client` "default implementation re-uses a client if name and root_dir" match — [`:help vim.lsp.Config`](https://neovim.io/doc/user/lsp.html#vim.lsp.Config) (local 0.12.4 runtime help).
- typescript-language-server's `tsserver.fallbackPath` "is used when tsserver.path is unspecified or invalid and tsserver isn't available via the current workspace" and should point at `typescript/lib/tsserver.js` — [typescript-language-server configuration.md](https://github.com/typescript-language-server/typescript-language-server/blob/HEAD/docs/configuration.md). The repo is active (pushed 2026-10-20, 2,583 stars — GitHub API).
- vtsls "By default … uses the TypeScript version bundled with the server"; `vtsls.typescript.globalTsdk` overrides and `vtsls.autoUseWorkspaceTsdk` switches to the workspace version; nvim-lspconfig says it "supports monorepos by default and will automatically find the tsconfig.json" and that "it is not recommended to enable both vtsls and ts_ls at the same time"; vtsls' maintainer calls it a "best-effort product"; since Vue language server v3 "requires vtsls to support TypeScript" — [vtsls docs](https://docsearch.algolia.com/mcp/docs/repo/yioneko/vtsls); [nvim-lspconfig vtsls.lua mirror](https://git.sudomsg.com/mirror/nvim-lspconfig/tree/lsp/vtsls.lua?h=docs). vtsls pushed 2026-10-21, 1,100 stars (GitHub API).
- typescript-tools.nvim: pure-Lua client speaking tsserver's native protocol "with a translation layer to LSP", "Supports multiple tsserver instances, and both local and global TypeScript installations", Mason-installed tsserver, `tsserver_path` with a fallback to a "standard path resolution strategy"; requires Neovim >= 0.11.0 and plenary.nvim; README still says "early beta"; last push **2025-11-18**, 2,154 stars, 84 open issues (GitHub API) — [typescript-tools.nvim README](https://github.com/pmizio/typescript-tools.nvim).
- Missing `node_modules` symptoms: "tsserver will generate a large number of errors in pretty much all TypeScript files" — [geekcoderjournal.substack.com](https://geekcoderjournal.substack.com/p/typescript-language-server-automatic?r=1c2kt); worktree guides state "node_modules not shared" and advise an install per worktree; pnpm "won't climb to the parent's node_modules" — [nuxt-setup skill](https://skills.cat/skills/martin-janci/claude-marketplace/nuxt-setup); [worktree-bootstrap skill](https://www.skills.sh/jakerains/agentskills/worktree-bootstrap). Zed had to "Ensure Typescript is present" for its Astro server because of missing `typescript.js`/`tsserverlibrary.js` — [zed commit](https://git.secluded.site/zed/commit/a0d687c24a2ed8d335504c83725396aeec17c6c5).
- gh.nvim's README explicitly motivates local checkout with "LSP and local dev environments work on it" — [gh.nvim README](https://github.com/ldelossa/gh.nvim). codediff.nvim's PR mode by contrast "reviews a PR without checking out its branch" (so no LSP on PR revisions) — [codediff.nvim README](https://github.com/esmuellert/codediff.nvim).

### Inferences
- Implementation: `git worktree add <stdpath('cache')/revuey/<repo>/<pr>> <ref>`; open files from it; rely on default `root_markers = { 'tsconfig.json', 'jsconfig.json', 'package.json', '.git' }`-style configs (nvim-lspconfig defaults) so a fresh `ts_ls`/`vtsls` client starts with the worktree as root. Because the worktree has its own `.git` file and `package.json`, root detection is unambiguous.
- `node_modules`: a symlink from the worktree to the main checkout's `node_modules` works for the common single-package case when lockfiles match, since Node/tsserver resolve through symlinked directories; it breaks for pnpm/yarn-PnP layouts, native modules keyed to the checkout, or monorepos with nested `node_modules`. The robust default is to try the symlink, then offer `npm ci`/`pnpm install` in the worktree as an async job. I found no source testing the symlink approach with tsserver specifically, so treat it as an engineering hypothesis.
- Server choice: `ts_ls` (user already has it) and `vtsls` are both maintained; `vtsls` has the better monorepo/tsdk story and is now required by the Vue ecosystem; typescript-tools.nvim has gone ~11 months without a push and still depends on the effectively-dead plenary, so it is the weakest choice for a new plugin.

### Gaps
- No primary source on tsserver behavior with a symlinked `node_modules` in a git worktree (only general "install per worktree" advice).
- Did not verify typescript-tools.nvim's exact TypeScript lookup order.

## Key Question 4: Async and AI API calls from Lua

### Takeaway
`vim.system()` (0.10+) and `vim.uv` are the standard async primitives; every major AI plugin (codecompanion, avante, CopilotChat) still shells out to `curl` for streaming HTTP, and 0.12 adds a minimal `vim.net.request()` (GET only). Reusing Claude Code's subscription OAuth token is explicitly disallowed by Anthropic since early 2026 and is server-side enforced, so an API key (or driving the `claude` CLI/ACP as a subprocess) is the only legitimate route.

### Cited Findings
- `vim.system({cmd}, {opts}, {on_exit})` exists in the Lua stdlib; `vim.net.request({url}, {opts}, {on_response})` "Makes an HTTP GET request to the given URL, asynchronously", with `outbuf`, `outpath`, `retry` (default 3) and a cancellable job — [`:help vim.net.request()`](https://neovim.io/doc/user/lua.html#vim.net.request()) (local 0.12.4 runtime help; GET only, no POST/streaming documented).
- codecompanion.nvim (6,899 stars, pushed 2026-10-20 — GitHub API) requires "The curl library and Neovim 0.10.0 or newer" and plenary.nvim; its HTTP client routes through `codecompanion.utils.curl` (`Curl.post`, `Curl.get`, `*_sync`), sets `--tcp-nodelay`/`--no-buffer` for streaming and delivers chunks via a `schedule_wrap`'d stream callback — [codecompanion README](https://github.com/olimorris/codecompanion.nvim); [codecompanion http.lua](https://raw.githubusercontent.com/olimorris/codecompanion.nvim/main/lua/codecompanion/http.lua). A user write-up shows running `claude setup-token` and passing `CLAUDE_CODE_OAUTH_TOKEN` to codecompanion's `claude_code` ACP adapter (personal dotfiles, Jan 2026, not official) — [notes.billmill.org](https://notes.billmill.org/computer_usage/vim/codecompanion.html).
- avante.nvim (18,189 stars, pushed 2026-10-20; repo now under `avante-corp` — GitHub API) is "only compatible with Neovim 0.11.0 or later", needs a `make` build step (Rust crates, prebuilt binaries fetched with `curl`/`tar`), lists plenary as required, supports providers openai/anthropic/mistral/deepseek/ollama/..., Copilot via copilot.lua, and ACP agents "codex, gemini, claude-code"; the Claude provider accepts `ANTHROPIC_API_KEY`/`AVANTE_ANTHROPIC_API_KEY` or `auth_type = "max"` for a browser-based Pro/Max login — [avante README](https://github.com/yetone/avante.nvim); [avante Claude provider docs](https://www.mintlify.com/yetone/avante.nvim/providers/claude).
- CopilotChat.nvim (3,649 stars, pushed 2026-10-12) requires "0.10.0+", "curl 8.0.0+", plenary.nvim, and routes Claude models through GitHub Copilot's model list — [CopilotChat README](https://github.com/CopilotC-Nvim/CopilotChat.nvim).
- Anthropic policy: "using OAuth tokens obtained through Claude Free, Pro, or Max accounts in any other product, tool, or service, including the Agent SDK, is not permitted"; developers are directed to API keys — [gigazine.net](https://gigazine.net/gsc_news/en/20260220-anthropic-third-party-block); [alternativeto.net](https://alternativeto.net/news/2026/2/anthropic-officially-bans-using-subscription-authentication-for-third-party-claude-use). Server-side checks reportedly began 2026-01-09, breaking OpenCode and others — [falcao.org](https://falcao.org/posts/anthropic-claude-access-crackdown-ecosystem-fallout/); one tracker lists 2026-04-04 as a further enforcement date (single source) — [tech-insider.org](https://tech-insider.org/ie/?p=560). Moltis documents why it refuses to support Anthropic OAuth — [docs.moltis.org](https://docs.moltis.org/anthropic-oauth.html).
- coder/claudecode.nvim (3,127 stars, pushed 2026-10-17 — GitHub API) integrates the Claude Code CLI over a WebSocket MCP protocol and requires the CLI installed — [claudecode.nvim listing](https://docsearch.algolia.com/mcp/docs/repo/coder/claudecode.nvim).

### Inferences
- A new plugin should use `vim.system({'curl', ...})` directly (no plenary) with a line-buffered stdout callback for SSE streaming; `vim.net.request` is not sufficient for POST/streaming as documented in 0.12.
- For users on a Claude subscription, the compliant path is to spawn `claude -p`/the Agent SDK or ACP from the plugin (as avante and codecompanion do), accepting the latency of a CLI subprocess; for API-key users call the Messages API directly.
- avante's `auth_type = "max"` almost certainly no longer works against Anthropic's servers; I found no avante commit removing it, only the policy change (inference).

### Gaps
- Whether avante/CopilotChat's HTTP layers use plenary.curl vs `vim.system` was not confirmed from source (codecompanion's wrapper internals also not read).
- No primary Anthropic document was fetched; policy facts come from multiple secondary news sources that agree with each other.

## Key Question 5: Persistence of per-repo review state

### Takeaway
The convention is JSON under `vim.fn.stdpath('data')` (or `'state'`/`'cache'`), keyed by repo path and/or branch; dimfeld's diffview fork is the directly relevant precedent (per-branch files keyed by blob hash so marks survive rebases), and durable.nvim offers SQLite if JSON becomes limiting. Writing into the repo's `.git` directory is not a pattern any surveyed plugin uses.

### Cited Findings
- `stdpath({what})` "Returns standard-path locations" driven by `$NVIM_APPNAME`/`$XDG_*` — [`:help stdpath()`](https://neovim.io/doc/user/builtin.html#stdpath()) (local 0.12.4 runtime help).
- harpoon stores state at `vim.fn.stdpath("data") .. "/harpoon.json"` and merges a config-dir file — [harpoon setup docs](https://www.mintlify.com/ThePrimeagen/harpoon/configuration/setup).
- persisted.nvim saves sessions under the data directory and "can create session files based on the branch of a git-enabled repository"; persistence.nvim uses the state directory — [persisted.nvim](https://fr.github.com/olimorris/persisted.nvim); [search summary](https://awesome.ecosyste.ms/projects/github.com%2Fwillothy%2Fdurable.nvim).
- durable.nvim is "a SQLite-backed key-value store and persistent objects for Neovim" — [durable.nvim listing](https://awesome.ecosyste.ms/projects/github.com%2Fwillothy%2Fdurable.nvim).
- dimfeld/diffview.nvim: review state "stored per branch", marking a file "saves its blob hash and a timestamp", default `~/.cache/diffview.nvim/reviews/`, `auto_cleanup`/`:DiffviewReviewCleanup` — [dimfeld README](https://github.com/dimfeld/diffview.nvim).
- diffview-plus `persist_selections` keeps file-panel selections across restarts — [diffview-plus README](https://github.com/dlyongemallo/diffview.nvim).
- octo.nvim persists nothing locally for reviews beyond GitHub itself (pending reviews live on GitHub; `Octo review resume`) — [octo README](https://github.com/pwntester/octo.nvim).

### Inferences
- For "logical chunk reviewed" state, key entries by `(file path, hunk content hash)` or `(blob hash, hunk header)` rather than line numbers so marks survive rebases and force-pushes, extending dimfeld's blob-hash idea to chunk granularity. Store under `stdpath('data')/revuey/<sha1 of repo root>/<branch>.json` and use `vim.json.encode`/`decode` (built-in).
- If the TUI and the Neovim plugin share a state format (e.g. the same JSON schema), the Neovim plugin can read/write the same file, which is the cheapest way to make a Neovim front-end interoperate with a non-Neovim engine.

### Gaps
- No surveyed plugin documents chunk-level (sub-file) review persistence; the design above is an inference.

## Key Question 6: Distribution and UX constraints (plugin-only reach, launching from an agent, embedding/inverse integration)

### Takeaway
A plugin reaches only Neovim users and needs their tree-sitter parsers and LSP setup to be present; launching it from an agent or tmux pane is easy (`nvim -c "Revuey pr 123"` or `nvim --server <sock> --remote-send`), and the inverse direction (a standalone TUI opening files in a running Neovim) is already a well-trodden pattern via `--listen`/`--server --remote` as used by lazygit.nvim.

### Cited Findings
- `nvim --listen <addr>` starts a server; `nvim --server <addr> --remote file.txt`, `--remote-tab`, and `--remote-send '<keys>'` drive it; `--servername`/`--serverlist` are "Not yet supported by Nvim" — [`:help remote`](https://neovim.io/doc/user/remote.html) (local 0.12.4 runtime help). `--embed` uses stdio as a msgpack-RPC channel and can be combined with `--headless` — [`:help --embed`](https://neovim.io/doc/user/starting.html#--embed) (local 0.12.4 runtime help).
- lazygit.nvim's README documents both neovim-remote (`nvr`) for the commit editor and a vanilla setup where Neovim is started with `--listen` and lazygit's `editCommandTemplate` runs `nvim --server /tmp/nvim-server.pipe --remote-tab {{filename}}` — [lazygit.nvim README](https://github.com/kdheepak/lazygit.nvim); a lazygit discussion notes the templated filename is relative to the repo root, complicating one-server-per-repo setups — [lazygit discussion #1956](https://fr.github.com/jesseduffield/lazygit/discussions/1956). Inside Neovim, `$NVIM` is set in terminal buffers, so a TUI can target it with `--server $NVIM` — [zenn.dev write-up](https://zenn.dev/rikson/articles/2024-05-26_rikson_lazygit-nvim-remote-integration).
- `nvim_open_term({buf}, {opts})` opens "a terminal instance in a buffer" (API for embedding TUIs); 0.12 shows "[Process exited]" as virtual text — [`:help nvim_open_term()`](https://neovim.io/doc/user/api.html#nvim_open_term()); [`:help news`](https://neovim.io/doc/user/news.html) (local 0.12.4 runtime help).
- `vim.pack` is the 0.12 built-in manager with `vim.pack.add()`, `update()`, `del()`, `get()` and a lockfile — [`:help vim.pack`](https://neovim.io/doc/user/pack.html) (local 0.12.4 runtime help); [tproger.ru summary](https://tproger.ru/news/neovim-0-12-0-poluchil-vstroennyj-menedzher-plaginov-vim-pack-i-ul).
- Prior art for agent-driven review inside Neovim: codediff.nvim is built so "Changes appear as they land while any coding agent works in the background" — [codediff README](https://github.com/esmuellert/codediff.nvim); claudecode.nvim links the Claude Code CLI to Neovim via WebSocket/MCP — [claudecode.nvim listing](https://docsearch.algolia.com/mcp/docs/repo/coder/claudecode.nvim).
- A terminal workflow (Josh Morony) already does "if the PR's branch is already checked out in one of your own worktrees it reuses that; otherwise it creates a managed worktree" from a shell handoff — [joshmorony.com](https://www.joshmorony.com/workflows/handoff-terminal-github-pr-review/).

### Inferences
- "Launch in a tmux pane" from an agent = `tmux split-window "nvim -c 'Revuey review <ref>'"`; no headless mode is needed for the interactive surface. `nvim --headless` is only useful for non-interactive tasks (e.g. generating the guided-review document from the plugin's Lua and exiting), which a TUI engine could call to reuse plugin logic.
- The inverse integration (standalone TUI + `nvim --server $NVIM --remote`) is already what lazygit users do and gives LSP/tree-sitter "for free" in the user's own editor, at the cost of the TUI not controlling rendering. A hybrid — TUI for workflow, `--remote` for "open at line" — is the cheapest way to serve non-Neovim users while still giving Neovim users jump-to-definition.
- Reach constraint: everything in KQ1 depends on the user having TypeScript/TSX parsers installed (not bundled) and an LSP configured; a plugin must `:checkhealth` for these and degrade (plain text + diff colors) when absent.

### Gaps
- No source describing a review plugin that exposes a headless/RPC API for agents; this is an unexplored design space.

## Key Question 7: Classic Vim compatibility

### Takeaway
Not worth it for this feature set. Vim 9.2 (Feb 2026) has a maturing Vim9 script language and even gained `diffanchors`/linematch, but it has no built-in LSP client, no tree-sitter, no extmarks/virtual lines, and no Lua stdlib; every rendering technique in KQ1 and every reusable plugin in KQ2 is Neovim-only.

### Cited Findings
- Vim 9.2 was released 2026-02-14 with Vim9-script enums, generic functions, tuples, fuzzy completion, a new linematch algorithm and `diffanchors`, experimental Wayland, XDG config, vertical tab panel, `:Tutor` — [heise.de](https://heise.de/-11177683); [helpnetsecurity.com](https://www.helpnetsecurity.com/2026/02/16/vim-9-2-released/); [phoronix.com](https://phoronix.com/news/Vim-9.2-Released). None of the release coverage mentions LSP or tree-sitter.
- LSP in Vim is a plugin concern: yegappan/lsp is "written only in Vim9 script", requires "Vim version 9.0 or above", and does not install servers — [yegappan/lsp](https://github.com/maximyurevich/lsp); it is active (pushed 2026-10-15, 790 stars, 113 open issues — GitHub API).
- Neovim is the project with "a built-in language server protocol (LSP) client" and bundled tree-sitter — [realpython.com](https://realpython.com/ref/code-editors-ides/neovim/).
- All the plugins surveyed state Neovim minimums (0.9–0.12) and are written in Lua (octo, gitlab.nvim, codediff, diffs.nvim, mini.diff, gitsigns, render-markdown, orgmode, avante, codecompanion) — see KQ2 citations. The only Vimscript plugin in scope, vim-fugitive, provides diff/blame but no review threads.

### Inferences
- Supporting Vim would mean a second implementation in Vim9 script with `text properties`/`popup` as a weaker substitute for extmarks, syntax-file highlighting instead of injections, and a third-party LSP client; none of the Lua code would carry over. For non-Neovim editors the `--remote`-style handoff from a TUI (KQ6) is the better reach strategy.

### Gaps
- I did not fetch Vim 9.2's official help to confirm the absence of any experimental tree-sitter integration; the conclusion rests on release coverage and the plugin ecosystem.
