## A1. How plannotator structures its Guided Review (prompt, schema, hunk references, rendering)

### Takeaway
Plannotator's Guided Review is a **file-level** (not hunk-level) chaptering of a diff: the model returns `{title, intent, sections[{title, overview, diffs[{file, summary}]}], unplacedFiles[]}`, enforced by `--json-schema` (Claude) / `--output-schema` (Codex) / a nonce-tagged marker block (Cursor/OpenCode/Pi/Copilot), validated server-side with a fail-closed "every changed file appears exactly once" coverage rule, and rendered by mounting the *same* diff viewer component per referenced file. Per-section `reviewed: boolean[]` state is stored beside the guide keyed by job id; a saved guide records the head SHA and shows "Diff changed" if the repo moved. Hunk-level slicing is explicitly out of scope.

### Cited Findings
- Docs: Guided Review "organizes the change into ordered sections with summaries and live diffs"; "Each successfully generated guide is saved under the data directory and can be reopened from Previous guides"; "Completion persists with the saved guide. A completed section starts collapsed on reopen"; a saved guide records "the repository commit present when it was generated" and shows **Diff changed** if the repo moved; engines detected "by checking for their command on PATH" (`claude`, `codex`, `agent` (Cursor), `opencode`, `pi`, `copilot`); "The command must also be authenticated and have a usable model configuration." — [plannotator docs: Agent reviews](https://docs.plannotator.ai/open-source/workflows/agent-reviews.md)
- Code Tour is a separate job ("a narrated walkthrough with checkpoints", Claude/Codex only) distinct from Guided Review and from Code Review (severity findings). — [plannotator docs: Agent reviews](https://docs.plannotator.ai/open-source/workflows/agent-reviews.md)
- Repo is dual-licensed Apache-2.0 / MIT, TypeScript on Bun; relevant paths: `packages/core/guide.ts` (types), `packages/core/guide-prompt.ts` (prompt + JSON schema + validator, browser-safe), `packages/server/guide/guide-review.ts` (engine command builders, parsers, repair, session), `packages/core/guide-format.ts` (portable snapshot format), `adr/specs/guided-review-20260702-195351.md`, `adr/decisions/006-…`, `adr/decisions/007-portable-guided-reviews-20260815.md`. — [GitHub backnotprop/plannotator](https://github.com/backnotprop/plannotator) (read from local clone at commit e439758c, 2026-10-21)
- **Output types** (`packages/core/guide.ts`): `GuideDiffRef { file: string; summary?: string }` ("Repo-relative path; must match a DiffFile.path in the current review patch"); `GuideSection { title; overview (markdown); diffs: GuideDiffRef[] }` with the comment "Semantic order (core first, consequences next, glue grouped last) is carried by the array position, not by any label field"; `CodeGuideOutput { title; intent; sections; unplacedFiles? }`; `CodeGuideData = CodeGuideOutput & { reviewed: boolean[]; saved?; moved? }`. — [plannotator packages/core/guide.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide.ts)
- **JSON Schema** (`GUIDE_SCHEMA_JSON`): object with `title`, `intent`, `sections[]` (each `{title, overview, diffs[{file, summary}]}` with `additionalProperties:false` and all fields required) and `unplacedFiles: string[]`; top-level required `["title","intent","sections","unplacedFiles"]`, `additionalProperties:false`. — [plannotator packages/core/guide-prompt.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-prompt.ts)
- **Prompt** (`GUIDE_REVIEW_PROMPT`, "Guided Review Organizer"): identity is "a senior engineer … organizing it into a guided review: an ordered sequence of chapters"; "You are NOT hunting for bugs"; ordering rule: "Order by IMPORTANCE, not by file path, diff size, or the order things happened … 1. The most important chapter comes first: the implementation heart … 2. Then the consequences, in decreasing signal … 3. Glue and low-signal changes come LAST, grouped together"; chunking rule: "A section is a logical unit of change, not a file and not a folder. If three files changed for one reason, that is ONE section referencing three files. If one file has two unrelated changes, split it into two sections"; coverage rule: "Every changed file must appear in EXACTLY ONE place: either in exactly one section's `diffs`, or in `unplacedFiles`"; "Typically 2-6 sections. Never more than 10"; voice rules (25-word sentence ceiling, no em-dashes, no emoji); research budget ("Do NOT explore the repository … If you catch yourself on a third exploratory tool call, stop"); overview = "what changed, why it exists, key implications", with optional `> [!IMPORTANT]` / `> [!WARNING]` callouts; per-file `summary` must be "written from the diff hunks you already have … Do NOT open the file". — [plannotator packages/core/guide-prompt.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-prompt.ts)
- The prompt is "MIRRORED VERBATIM into the standalone `guided-review` agent skill (github.com/plannotator/guides, skills/guided-review/SKILL.md)" so an agent can write `guide.json` + `guide.patch` and the CLI wraps it. — [plannotator packages/core/guide-prompt.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-prompt.ts); [ADR 007 D9](https://github.com/backnotprop/plannotator/blob/main/adr/decisions/007-portable-guided-reviews-20260815.md)
- **User message** (`buildGuideUserMessage`): appends a "Changed files (plan section placement against this exact file set; diffs[].file must match one of these paths verbatim):" block with `path (+adds/-dels)` per file; inlines the patch in a ```diff fence for local diffs/Bitbucket/full-stack PRs; for PRs with local checkout tells the model to run `git diff origin/<base>...HEAD`. — [plannotator packages/core/guide-prompt.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-prompt.ts)
- **Claude invocation** (`buildGuideClaudeCommand`): `claude -p --permission-mode dontAsk --output-format stream-json --verbose --json-schema <schema> --no-session-persistence --model <model, default "sonnet"> [--effort X] --tools … --setting-sources user --strict-mcp-config --append-system-prompt <shell guidance>`, prompt via stdin; structured output read from the NDJSON `result` event's `structured_output`. Read-only allowlist (`Agent, Read, Glob, Grep, Bash(git diff:*)`, etc.) plus deny list (`Edit, Write, WebFetch, curl, python…`). — [plannotator packages/server/guide/guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts); [packages/server/claude-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/claude-review.ts)
- **Codex invocation** (`buildGuideCodexCommand`): `codex [-m model] [-c model_reasoning_effort=X] [-c service_tier=fast] exec --output-schema <schema file> -o <output file> --approve-for-me --ephemeral -C <cwd> <prompt>`; the final JSON is read from the `-o` file. Comment: "Global flags must precede the 'exec' subcommand for the Codex CLI." — [plannotator packages/server/guide/guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)
- **Marker engines** (Cursor `agent`, `opencode`, `pi`, `copilot`): "None of the three has a schema flag, so the marker-delimited JSON block is the only way to get structured output back"; the prompt appends an "Output contract" with a per-job nonce tag `<plannotator-review-json:pn…>` and a prose schema; parser takes the LAST complete nonce-scoped block from NDJSON stdout. — [plannotator packages/server/guide/guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)
- **Robustness**: mechanical JSON repair (`repairGuideJsonText`: strip fences, slice first `{`..last `}`, strip trailing commas outside strings, close unbalanced brackets), a "repair" job that asks the model to fix only syntax ("NEVER change the content"), and manual paste-in repair; failed payloads stashed (200 KB cap). — [plannotator packages/server/guide/guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)
- **Validation** (`validateGuideOutput`): "the model is instructed but not trusted"; spec: "`diffs[].file` not in the current DiffFile set → ref discarded entirely (a fabricated path never surfaces)"; "every changed file must appear exactly once across sections + unplacedFiles (server enforces by diffing the sets)"; zero sections → job failed. Validation runs against the **launch-time** changed-file snapshot "so a mid-generation diff/base/PR switch never invalidates an otherwise-valid guide". — [plannotator adr/specs/guided-review](https://github.com/backnotprop/plannotator/blob/main/adr/specs/guided-review-20260702-195351.md); [guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)
- **Original v1 spec had hunk hints and section kinds that were dropped**: spec draft had `GuideDiffRef { file; lineStart?; lineEnd?; note? }` ("optional highlight hint (new side), not a slicing boundary") and `GuideSection.kind: "core"|"consequence"|"support"`; shipped types have neither. Spec explicitly lists "hunk-level slicing" as out of scope for v1. — [plannotator adr/specs/guided-review](https://github.com/backnotprop/plannotator/blob/main/adr/specs/guided-review-20260702-195351.md)
- **Reviewed state & staleness semantics** (spec): "Reviewed checkboxes are per-section (v1: no per-diff checkbox)"; "Reviewed state keyed by jobId … Regenerating creates a new job → fresh reviewed state"; "guide renders whatever the *current* files array holds … refs that don't [resolve] show the outdated chip and a 'Regenerate guide' affordance. The guide never pins its own patch copy." (Later superseded for export: ADR 007 D6 captures the launch-time patch beside the saved guide as `{id}.patch`.) — [spec](https://github.com/backnotprop/plannotator/blob/main/adr/specs/guided-review-20260702-195351.md); [ADR 007](https://github.com/backnotprop/plannotator/blob/main/adr/decisions/007-portable-guided-reviews-20260815.md)
- **Rendering**: `GuideView → GuideSectionCard → GuideFileCard → GuideViewportManager → AllFilesCodeView` on `@pierre/diffs`; `GuideDiffSection` is "a thin ReviewDiffPanel-style adapter: resolves `files.find(f => f.path === ref.file)`, mounts one DiffViewer + ToolbarHost wired to the same handleAddAnnotation; missing file → 'outdated' chip". Annotations made in the guide "are ordinary CodeAnnotations — same state, same Send Feedback payload". A reviewed section "collapses to a single row". — [spec](https://github.com/backnotprop/plannotator/blob/main/adr/specs/guided-review-20260702-195351.md); [ADR 007 D2](https://github.com/backnotprop/plannotator/blob/main/adr/decisions/007-portable-guided-reviews-20260815.md)
- **Portable snapshot format** (`GuideSnapshotV1`): `{ kind: "plannotator-guided-review", version: 1, exportedAt, guide: CodeGuideOutput & {reviewed: boolean[]}, review: { rawPatch, gitRef, diffType?, base? }, source: { kind: local|pr|workspace|commit, repo?, branch?, headSha?, pr?{url,number,title,platform}, commitSha? }, generator?: { engine, model, generatedAt, customInstructions }, theme? }`; "Parsing rejects unknown fields"; exported HTML embeds the JSON in `<script type="application/json" id="plannotator-guided-review">` and loads a pinned, content-hashed viewer from `guides.show/v1/…`. — [plannotator packages/core/guide-format.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-format.ts); [ADR 007](https://github.com/backnotprop/plannotator/blob/main/adr/decisions/007-portable-guided-reviews-20260815.md)
- Saved guide list entry: `{ id, label, title, savedAt, progress: {reviewed, total}, moved: boolean }` where `moved` = "True when the stored head sha differs from the current head". History can be disabled with `PLANNOTATOR_GUIDE_HISTORY=0`. — [guide.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide.ts); [docs](https://docs.plannotator.ai/open-source/workflows/agent-reviews.md)

### Inferences
- Plannotator deliberately traded hunk precision for robustness: file paths are easy to validate against the changed-file set, while line ranges hallucinate and drift. Their coverage rule ("exactly once") is the single most useful invariant to copy.
- Because the guide renders the *live* diff for each file (not a captured excerpt), there is no second diff representation to keep in sync; staleness is handled at file granularity (missing path → "outdated" chip) and at guide granularity (head SHA mismatch → "Diff changed").
- Their multi-engine design shows the practical spectrum: schema-enforced CLIs (Claude `--json-schema`, Codex `--output-schema`) vs. prompt-only marker blocks for everything else, plus mechanical JSON repair. A new tool can start with the two schema-enforced paths.

### Gaps
- I did not read the client React components or `validateGuideOutput`'s exact handling of duplicate paths (the spec says duplicates are reconciled server-side; the exact precedence rule was not read).
- Plannotator's "Code Tour" prompt/schema (checkpoints) was not read; it may contain line-level anchoring worth checking (`packages/server/tour/tour-review.ts`).

## A2. How other tools present narrative review (CodeRabbit, Graphite, Copilot, Greptile, Ellipsis, Bugbot, Claude Code, Amp, others)

### Takeaway
Almost every hosted AI reviewer produces a **summary + walkthrough table + inline findings**, not an ordered reading path. The only products found that reorder the diff for reading are plannotator's Guided Review (chaptered, file-level) and Amp's "Intelligently Ordered Diffs" (file reordering with muted low-signal files, no prose). No vendor publishes a schema for walkthrough output; CodeRabbit publishes the configuration knobs that toggle walkthrough sections.

### Cited Findings
- **CodeRabbit** walkthrough is a single collapsible comment composed of toggleable parts: `reviews.high_level_summary` ("Generate a high-level summary of the changes in the PR description or walkthrough", default true), `reviews.changed_files_summary` ("Include a summary of the changed files in the walkthrough", true), `reviews.sequence_diagrams` (true), `reviews.estimate_code_review_effort` (true), `reviews.related_prs`, `reviews.related_issues`, `reviews.assess_linked_issues`, `reviews.suggested_labels`, `reviews.suggested_reviewers`, `reviews.poem` (default false), `reviews.collapse_walkthrough` ("Wrap the walkthrough in a Markdown collapsible section", true), `reviews.review_info` ("configuration used, reviewed commits, and skipped files"). — [CodeRabbit configuration reference](https://docs.coderabbit.ai/reference/configuration)
- **Graphite**: "Diamond" has been renamed; the reviewer is now "AI Reviews" run by "Graphite Agent"; Graphite positions on low false positives (claims a 96% positive feedback rate on comments). No ordered-walkthrough feature found. (Secondary/vendor sources.) — [Graphite guide](https://graphite.com/guides/best-ai-pull-request-reviewers-2025); [Morph comparison](https://www.morphllm.com/comparisons/graphite-vs-coderabbit)
- **Greptile**: "posts feedback as a PR summary + inline comments" with "confidence scores, suggested fixes, and diagrams"; March 2026 changelog adds a "Fix All" button in the summary. — [Greptile docs: first PR review](https://www.greptile.com/docs/code-review/first-pr-review.md); [Greptile changelog](https://www.greptile.com/docs/changelog)
- **Cursor Bugbot**: top-level summary comment (Overview + Risk sections, also writable into the PR description as a `CURSOR_SUMMARY` block) separate from inline findings; forum reports it goes stale when re-runs are skipped. — [Cursor forum](https://forum.cursor.com/t/bugbot-summary-comment-not-updated-after-fixes-are-pushed/154935); [Cursor forum](https://forum.cursor.com/t/pr-cursor-summary-not-refreshed-when-bugbot-skips-re-run-after-offline-stored-review/166803)
- **Ellipsis**: "opens a pull request to get an AI Code Review and summary", updates the summary as commits are pushed; fills in PR descriptions. — [Ellipsis quickstart](https://docs.ellipsis.dev/quickstart)
- **GitHub Copilot PR summary**: "can summarize a pull request in the description field or as a comment"; inserted via Copilot icon → Summary; "does not take into account any existing content in the pull request description". No ordering/grouping described. — [GitHub Docs](https://docs.github.com/en/copilot/using-github-copilot/using-github-copilot-for-pull-requests/creating-a-pull-request-summary-with-github-copilot)
- **Claude Code Code Review (hosted, Team/Enterprise)**: four stages "Find → Verify → Rank → Post"; output is "inline comments on the lines concerned, with a summary in the review body" plus a check run; "Findings arrive … ranked by severity"; no model choice; review levels Quick/Standard/Deep. Local `/code-review` runs in your session on any plan; Ultrareview runs in a cloud sandbox. — [Claude Code docs: Code Review](https://code.claude.com/docs/en/code-review)
- **Amp "Intelligently Ordered Diffs"** (2026-09-01): "Amp reads the diff, finds the files that best explain the change, and moves them to the top"; "Less relevant files, such as tests, fixtures, and generated code, will be shown in muted colors below the important ones"; toggle between alphabetical and intelligent order; "a blue dot over the button will indicate that there is an updated ordering" when the diff changes. Whole-file ordering only; no prose, no hunk grouping. — [Amp news](https://ampcode.com/news/intelligently-ordered-diffs)
- Plannotator's own prompt mandates "entry point first, definitions before consumers, cause before effect", i.e. an explicit reading-order heuristic. — [plannotator guide-prompt.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-prompt.ts)

### Inferences
- The market's dominant "walkthrough" is a *table of files with one-line summaries* (CodeRabbit's `changed_files_summary`), which is structurally the same data as plannotator's `diffs[{file, summary}]` minus the chaptering and ordering. A schema that nests file summaries inside ordered chapters is a superset of what CodeRabbit emits and can degrade to it.
- Amp's "updated ordering" blue dot is a good pattern for guide staleness: regenerate in the background and offer to swap, rather than invalidating the reviewer's progress.

### Gaps
- Sourcegraph, "Dove", Gumroad's Flexile review, and Sturdy: no results found in this research pass; Sturdy (sturdy.dev) shut down in 2022 per my prior knowledge, unverified here. Graphite's current walkthrough format was not confirmed from Graphite's own docs (vendor pages fetched were marketing).
- No vendor publishes a JSON schema or the prompt for its walkthrough; only plannotator's is open.

## A3. Academic / industry work on diff decomposition, untangling, and reading order

### Takeaway
Three bodies of work inform chunk grouping: (1) **untangling** tangled commits into independent concerns (CLUSTERCHANGES at Microsoft, Flexeme, SmartCommit, CoRA, EpiceaUntangler), typically via def-use / dependency graph clustering; (2) controlled experiments showing decomposition reduces reviewer cognitive load; (3) **file ordering** studies (JetBrains 2023; ICSE 2026 survey; Sept 2026 arXiv) showing alphabetical order is not neutral, reviewers comment more on files shown first, and developers want dependency-aware grouping and customizable ordering.

### Cited Findings
- **CLUSTERCHANGES** (Barnett et al., Microsoft Research, ICSE 2015, "Helping developers help themselves: Automatic decomposition of code review changesets"): "understanding a review is harder when the changeset contains multiple independent code differences"; introduces an automatic decomposition technique (def-use relationships across the changeset). — [Microsoft Research](https://www.microsoft.com/en-us/research/publication/helping-developers-help-themselves-automatic-decomposition-of-code-review-changesets/)
- **Flexeme** (ESEC/FSE 2020): builds a multiversion program dependency graph (δ-NFG) and applies agglomerative clustering with graph similarity; reports accuracy 0.81 on C#, "0.14 above the prior state of the art", 32× faster. — [ESEC/FSE 2020](https://2020.esec-fse.org/details/fse-2020-papers/27/Flexeme-Untangling-Commits-Using-Lexical-Flows); [UCL PDF](https://discovery-pp.ucl.ac.uk/10107163/2/Barr_Flexeme-%20Untangling%20Commits%20Using%20Lexical%20Flows_AAM.pdf)
- **SmartCommit** (ESEC/FSE 2021, Distinguished Paper): graph-partitioning, interactive decomposition; "median accuracy between 71–84% when decomposing composite commits without developer involvement"; field study with 83 engineers + 3,000 synthetic composite commits. — [ESEC/FSE 2021](https://2021.esec-fse.org/details/fse-2021-papers/20/SmartCommit-A-Graph-Based-Interactive-Assistant-for-Activity-Oriented-Commits)
- **CoRA** (ASE 2019): decomposes a commit into parts (bug fix / feature / refactor) using dependency analysis and tree-based similar-code detection, ranks important changes with PageRank + heuristics, and *describes* each part; 6.3% accuracy improvement over state of practice. — [ASE 2019](https://www.se.cs.uni-saarland.de/conferences/ASE/ase2019/details/ase-2019-papers/33/CoRA-Decomposing-and-Describing-Tangled-Code-Changes-for-Reviewer.html)
- **EpiceaUntangler** (Dias et al. 2015, "Untangling Fine-Grained Code Changes"): clusters IDE-captured fine-grained edits; median 91% success. — [arXiv 1502.06757](https://www.arxiv.org/pdf/1502.06757)
- **ChangeBeadsThreader** (2020): interactive environment for tailoring automatically untangled changes. — [arXiv 2003.14086](https://ar5iv.labs.arxiv.org/html/2003.14086)
- **Controlled experiment on change decomposition** (Di Biase et al., PeerJ CS 2019 / arXiv 1805.10978): tangled changes "can hinder review by increasing reviewers' cognitive load" and noise "could put a reviewer on a wrong track"; cites Uwano et al. eye-tracking: reviewers follow a "scan" pattern reading the whole change before line-level inspection, and those who scan too little take longer to find defects. — [arXiv 1805.10978](https://arxiv.org/pdf/1805.10978); [PeerJ](https://peerj.com/articles/cs-193/)
- **File ordering, JetBrains/IntelliJ (EASE 2023, "Assessing the Impact of File Ordering Strategies on Code Review Process")**: ordering by code diff "significantly outperforms Alphabetical in MRR and nDCG" though effect sizes are small (<0.2); "reviewers leave more comments on the files shown higher in the code review". — [arXiv 2306.06956](https://arxiv.org/abs/2306.06956v1)
- **"Breaking the Alphabet: Rethinking File Ordering in Code Review" (ICSE 2026)**: survey of 1,355 developers; "only 10.2% of reviewers consider alphabetical ordering optimal"; customizable ordering requested by 66%. — [ICSE 2026](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/310/Breaking-the-Alphabet-Rethinking-File-Ordering-in-Code-Review); [Zenodo replication](https://zenodo.org/records/17634647)
- **"Not One to Rule Them All: Mining Meaningful Code Review Orders From GitHub"** (2025). — [arXiv 2506.10654](https://arxiv.org/pdf/2506.10654)
- **"Does Order Matter?" (Rahman, Codabux, Roy; arXiv 2609.22610, 18 Sep 2026)**: 330,343 multi-file PRs; latent bug rate rises from 56.7% at file position 1 to 61.5% at position 30; each additional file reduces odds of any review comment by ~8.7%; proposes "context-aware file ordering, dependency-aware grouping, risk-aware prioritization, and per-file coverage indicators". — [arXiv 2609.22610](https://arxiv.org/abs/2609.22610)

### Inferences
- The literature's grouping signal is **def-use / dependency edges between hunks**; an LLM organizer can approximate this cheaply, but a tool could pre-compute symbol-level overlap between hunks (same identifier defined in hunk A and used in hunk B) and feed it to the model as hints, or use it to validate the model's grouping.
- "Per-file coverage indicators" (2026 paper) is academic support for per-chunk "reviewed" state; "risk-aware prioritization" supports a `risk`/`attention` field per chunk.

### Gaps
- Google Critique and Meta Phabricator internal ordering: no public sources found describing diff ordering features.
- "ChangeScribe" appears to be a commit-message generator (Cortés-Coy et al. 2014) rather than a decomposer; not verified in this pass.

## A4. Schema design: anchoring chunks to hunks robustly, and how review platforms persist "reviewed" state (GitHub precisely, Gerrit, Reviewable, Bitbucket, GitLab, Crucible)

### Takeaway
Industry practice is **per-file, per-reviewer, per-revision** reviewed flags that are cleared (GitHub: state becomes `DISMISSED`, "The file has new changes since last viewed") when the file's content changes after viewing. Gerrit stores a reviewed flag per `(change, revision, file, account)`. Reviewable ties marks to revisions and considers a file done only when "marked reviewed at the most recent revision". None of these anchor below file granularity, so a hunk-level guide needs its own anchor: path + hunk header + line range + content hash, with graceful degradation to file-level.

### Cited Findings
- **GitHub "Viewed" behaviour (docs)**: "After you finish reviewing a file, you can mark the file as viewed. The file will collapse." and "If the file changes after you view the file, it will be unmarked as viewed." — [GitHub Docs: Reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)
- **GitHub (blog, 2019-07-01, updated 2021-05-14)**: "If a file is changed after you've viewed it, the status is removed and a 'Changed since last view' badge appears". — [GitHub Blog: Mark files as viewed](https://github.blog/news-insights/product-news/mark-files-as-viewed/)
- **GitHub GraphQL (verified by live introspection via `gh api graphql` on 2026-10-21)**: enum `FileViewedState` = `DISMISSED` ("The file has new changes since last viewed."), `VIEWED` ("The file has been marked as viewed."), `UNVIEWED` ("The file has not been marked as viewed."); `PullRequestChangedFile` fields: `additions, changeType, deletions, path, viewerViewedState` ("The state of the file for the viewer."); mutation `markFileAsViewed(input: { pullRequestId, path, clientMutationId })` (and `unmarkFileAsViewed`). State is per-viewer and keyed by **path**, not by hunk. — GitHub GraphQL schema introspection (docs index: [GitHub GraphQL reference](https://docs.github.com/en/graphql/reference/enums))
- **Gerrit REST**: `PUT /changes/{change-id}/revisions/{revision-id}/files/{file-id}/reviewed` "Marks a file of a revision as reviewed by the calling user" (201 Created; 200 if already); `DELETE …/reviewed` "Deletes the reviewed flag of the calling user from a file of a revision" (204). I.e. flag scope = (change, revision/patch set, file, account). — [Gerrit REST API: Changes](https://gerrit-review.googlesource.com/Documentation/rest-api-changes.html)
- **Reviewable**: PR split into "revisions" ("an automatic, unmodifiable capture of one or more commits"); a file is complete when "marked reviewed at the most recent revision by at least one person who isn't acting as the pull request author"; reviewers who "most recently marked as reviewed a file that is not reviewed at the latest revision" go on the waiting-on list; "Show Unreviewed Diffs" shows the delta since the last reviewed revision; author self-marks "don't count towards review completion by default". — [Reviewable docs: Reviews](https://docs.reviewable.io/reviews.html)
- **Bitbucket Cloud**: resets viewed state for files altered by new commits to the source branch. — [Atlassian blog](https://www.atlassian.com/blog/bitbucket/stay-focused-by-marking-pr-files-as-reviewed)
- **GitLab (VS Code extension MR)**: per-file reset when a new push changes a file's diff; notes the web UI stores viewed state in browser localStorage. — [GitLab MR 3234](https://gitlab.com/gitlab-org/gitlab-vscode-extension/-/merge_requests/3234)
- **Crucible**: opening a file marks it read automatically; tracks viewed files across revisions for iterative reviews. — [Atlassian Crucible docs](https://confluence.atlassian.com/x/oAwaGg)
- **Phabricator**: tracks reviewer status (accepted/commented) per reviewer, not per file. — [Phabricator commit](https://secure.phabricator.com/rP370c7635a788ff7efd71f4ae6a5fd92c6b841be3)
- Plannotator (for comparison) keys reviewed state per section by job id, persists it with the saved guide, and records head SHA to flag "Diff changed" at guide granularity; file refs that no longer resolve show an "outdated" chip. — [plannotator spec](https://github.com/backnotprop/plannotator/blob/main/adr/specs/guided-review-20260702-195351.md); [docs](https://docs.plannotator.ai/open-source/workflows/agent-reviews.md)

### Inferences (schema design recommendations, derived from the above)
- **Anchor model**: each chunk references one or more `hunkRefs`, each `{ path, oldPath?, hunk: { oldStart, oldLines, newStart, newLines }, newLineRange?: [a,b], contentHash: sha256(normalized hunk body), fileHash?: sha256(new blob) }`. Resolve at render time: exact `contentHash` match → fresh; same `path` + overlapping new-line range but hash differs → "changed since reviewed" (mirror GitHub's `DISMISSED`); path missing → "outdated". This degrades to plannotator's file-level behaviour when hunk matching fails.
- **Reviewed-state invalidation** (copy GitHub semantics at chunk granularity): store `reviewed: { chunkId → { at, anchorHashes[] } }`; a chunk flips to `dismissed` when any of its anchored hunk hashes changes on regeneration/new push, while unaffected chunks keep `viewed`. Keep the guide's `baseSha`/`headSha` like plannotator so a whole-guide "Diff changed" banner is cheap.
- **Coverage invariant**: adopt plannotator's rule at hunk level: every hunk appears in exactly one chunk or in an explicit `unplaced` list; validate server-side against the parsed diff (model instructed but not trusted). Let the model reference hunks by a stable *index* you assign (`h12`) rather than by line numbers to cut hallucinated ranges; map indices back to anchors yourself.
- **Stable chunk IDs across regeneration**: derive `chunkId` from a hash of the sorted set of hunk anchors (not from the title) so a re-run that produces the same grouping inherits reviewed state; chunks whose anchor sets change get new IDs (or fuzzy-match by Jaccard overlap of hunks ≥ 0.5 to carry state across).
- Per-chunk optional fields the research supports: `order` (array position), `role: core|consequence|support` (plannotator v1 spec, later dropped but useful for muting glue like Amp), `risk: low|medium|high` (2026 paper's "risk-aware prioritization"), `callouts[]`.

### Gaps
- No public source describes GitHub's server-side implementation detail (e.g. whether "changed" is detected by blob SHA or by diff hunk content). The observable contract is "file changed after view → unmarked / DISMISSED".
- I did not verify GitLab web UI viewed-state storage beyond the extension MR's note.

## A5. Reusing one diff view component for main diff and guide excerpts

### Takeaway
Plannotator's answer is structural reuse: the guide mounts the same `AllFilesCodeView`/`DiffViewer` per referenced file in `readOnly`/annotatable modes, draws from a single `files` array (or, for exports, from one captured `rawPatch`), and reserves an annotation slot so the same comment state flows through both surfaces.

### Cited Findings
- ADR 007 D2: "One renderer, two hosts … moves into a package `@plannotator/guide-viewer` and Plannotator's review app imports it from there. 'No visual drift' is therefore structural, not a promise. `AllFilesCodeView` is reused behind a `readOnly` mode rather than replaced by a lean sibling; the annotation/edit machinery code-splits out for read-only hosts. Rejected: a separate lean diff renderer (would drift on the first Pierre upgrade…)". — [plannotator ADR 007](https://github.com/backnotprop/plannotator/blob/main/adr/decisions/007-portable-guided-reviews-20260815.md)
- Spec: guide takeover CSS-hides the dock/file tree "never unmount `<DockviewReact>`"; focus arbitration is solved by nulling `focusedFilePath` at the context level when `guideOpen` so hidden dock diff viewers "lose focus claims at the source". — [plannotator spec](https://github.com/backnotprop/plannotator/blob/main/adr/specs/guided-review-20260702-195351.md)
- Exported guide draws diff panes "from `rawPatch` and nothing else"; grammars shipped per-language and fetched on demand; a worker-pool/main-thread highlighting switch. — [plannotator guide-format.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-format.ts); [ADR 007 D8](https://github.com/backnotprop/plannotator/blob/main/adr/decisions/007-portable-guided-reviews-20260815.md)

### Inferences
- For a TUI (e.g. a Rust/ratatui tool like tuicr), the equivalent is: one `DiffFile`/`Hunk` model, one hunk renderer taking `(hunk, highlight range?, annotations)`, and a guide view that iterates chunk → hunkRefs → resolved hunks and calls the same renderer. Keep guide excerpts as *references into the parsed diff*, never as copied text, so comments, viewed state and syntax highlighting share one source of truth.

### Gaps
- No TUI-specific precedent found; the only concrete reuse design read is plannotator's web implementation.

## B1. Claude Code credentials on disk, token format, and Anthropic's policy on third-party use (with 2025–2026 timeline)

### Takeaway
Claude Code stores subscription OAuth in the macOS Keychain (service `Claude Code-credentials`, account = OS username; verified locally) or `~/.claude/.credentials.json` (0600; Linux, and macOS fallback), with env overrides `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` and the `apiKeyHelper` setting. Anthropic's current legal page (read 2026-10-21) says OAuth is "intended exclusively" for subscription plans' "ordinary use of Claude Code and other native Anthropic applications", that developers building products "should use API key authentication", and that developers "may not collect, store, or intermediate Claude.ai credentials or session tokens". The safe paths for a third-party local tool are: (1) user-supplied API key, or (2) spawning the unmodified `claude -p` binary (or the Agent SDK) and letting it use the user's own login, which Anthropic's support article and the legal page both explicitly allow. Reading the keychain/credentials file and calling the API directly with the OAuth token is what triggered the Jan–Feb 2026 enforcement and is prohibited.

### Cited Findings
**Storage and env vars (Anthropic docs, current):**
- "On macOS, credentials are stored in the encrypted macOS Keychain. When the Keychain rejects the write, such as when it's locked in an SSH session, Claude Code stores your login in `~/.claude/.credentials.json` with file mode `0600` instead, the same storage it uses on Linux." Windows: `%USERPROFILE%\.claude\.credentials.json`. With `CLAUDE_CONFIG_DIR` set, the file lives under that dir and "keys the macOS Keychain entry to that directory too". — [Claude Code docs: Authentication](https://code.claude.com/docs/en/authentication)
- Local verification (this machine, macOS, Claude Code 2.1.302): `security find-generic-password -s "Claude Code-credentials"` returns a `genp` item with `svce`=`acct`… service `"Claude Code-credentials"`, account `"dave"` (OS user); no `~/.claude/.credentials.json` exists. (Keychain item names are not documented by Anthropic; observed.)
- **Precedence** (docs): 1. cloud provider creds when `CLAUDE_CODE_USE_BEDROCK/VERTEX/FOUNDRY`; 2. `ANTHROPIC_AUTH_TOKEN` ("Sent as the `Authorization: Bearer` header", for gateways); 3. `ANTHROPIC_API_KEY` ("Sent as the `X-Api-Key` header … In non-interactive mode (`-p`), the key is always used when present"); 4. `apiKeyHelper` script output; 5. `CLAUDE_CODE_OAUTH_TOKEN` ("A long-lived OAuth token generated by `claude setup-token`"); 6. Anthropic profile / WIF credentials (`~/.config/anthropic`, `ANTHROPIC_PROFILE`, `ant auth login`); 7. - **Token/file format (community-reported, not Anthropic-documented)**: `.credentials.json` holds a `claudeAiOauth` object with `accessToken`, `refreshToken`, `expiresAt`, `scopes`, `subscriptionType`; a GitHub issue reports headless servers fail with 401 after expiry instead of refreshing. — [anthropics/claude-code issue #50743](https://github.com/anthropics/claude-code/issues/50743); [claudeissues.com #21765](https://claudeissues.com/issue/21765-oauth-refresh-token-not-used-when-credentials-are-copied-to-remote-headless-mach)

### Inferences
- For a local review tool, the only defensible Anthropic paths are: (a) `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` / `apiKeyHelper` / `ant auth` profile from the user's environment, using the official SDK; (b) subprocess `claude -p` (unmodified binary) with `--output-format json --json-schema`, which uses the user's own login legitimately and (per the support article) draws on their subscription/credits. Plannotator does exactly (b) and detects engines by PATH presence only; it never reads credentials.
- Do **not** read `~/.claude/.credentials.json` or the `Claude Code-credentials` keychain item, and do not accept a pasted `CLAUDE_CODE_OAUTH_TOKEN` as an API credential for direct API calls: that is "collect, store, or intermediate Claude.ai credentials or session tokens" and matches the "spoofing the harness" behaviour that was blocked server-side. Technically it also breaks on refresh (reported 401s) and needs the undocumented `anthropic-beta: oauth-2025-04-20` header.
- A reasonable *detection-only* use of the credential store is to answer "is the user logged into Claude Code?" (e.g. `claude auth status`-style check, or `security find-generic-password -s "Claude Code-credentials" >/dev/null`) to decide whether to offer the `claude -p` engine; even that is better done by invoking `claude` itself.

### Gaps
- Anthropic has no published spec for the keychain item or the `.credentials.json` fields; all field names are community-reported.
- Exact dates of the April 4 restriction and its reversal come from VentureBeat/other press; I found no primary Anthropic post for April 4. The @ClaudeDevs tweet is cited by VentureBeat but was not fetched.
- Whether `claude -p` run from a third-party tool bills to "Agent SDK credits" vs. normal subscription limits after Oct 7, 2026 is only partially described in the support article; the article's full text could not be quoted beyond short excerpts.

## B2. OpenAI / Codex: auth storage, ChatGPT-login tokens vs API keys, and policy on third-party reuse

### Takeaway
Codex caches ChatGPT-login or API-key credentials in `~/.codex/auth.json` (or the OS keyring, per `cli_auth_credentials_store = file|keyring|auto|ephemeral`), refreshes ChatGPT tokens automatically, and OpenAI's docs say to treat the file "like a password" and that "API keys are still the recommended default for automation". OpenAI's sanctioned route for third-party apps to use a user's ChatGPT plan is **Sign in with ChatGPT** (SIWC) with an opt-in "ChatGPT plan usage" capability, documented for "open-source and locally hosted apps" and requiring `store:false`, `stream:true` and a persisted `ext_agent_host_id`; paid/hosted apps must apply via an interest form. No OpenAI text was found that explicitly permits or forbids reading `~/.codex/auth.json` from another tool; the public API is reported (secondary) not to accept the ChatGPT token as a bearer key, which is why tools proxy through Codex-shaped requests. Shelling out to `codex exec --output-schema` is the zero-config path.

### Cited Findings
- "Codex caches login details locally in a plaintext file at `~/.codex/auth.json` or in your OS-specific credential store"; `cli_auth_credentials_store` values `file` (auth.json under `CODEX_HOME`, default `~/.codex`), `keyring` ("fails if it is unavailable"), `auto`, `ephemeral` ("in memory for the current process only"); admins can enforce it. — [Codex docs: Authentication](https://learn.chatgpt.com/docs/auth)
- "For sign in with ChatGPT sessions, Codex refreshes tokens automatically during use before they expire"; ChatGPT sign-in "gives subscription access and follows ChatGPT workspace permissions, RBAC, and retention settings"; API-key sign-in is "usage-based access, billed at standard API rates". — [Codex docs: Authentication](https://learn.chatgpt.com/docs/auth)
- API key login: `printenv OPENAI_API_KEY | codex login --with-api-key`; enterprise "Codex access tokens": `printenv CODEX_ACCESS_TOKEN | codex login --with-access-token`, "intended for trusted scripts, schedulers, and private CI runners"; "For general OpenAI API calls, continue to use Platform API keys." Device code: `codex login --device-auth` (beta, must be enabled in ChatGPT security settings). Headless: prefer device code; fallback "copy `~/.codex/auth.json` to the headless machine"; "API keys are still the recommended default for automation"; "Treat `auth.json` like a password, and don't commit, paste, or share it." — [Codex docs: Authentication](https://learn.chatgpt.com/docs/auth)
- `codex login status` "Print the active authentication mode and exit with 0 when logged in"; `codex logout` "Remove saved credentials for both API key and ChatGPT authentication." — [Codex CLI reference](https://learn.chatgpt.com/docs/cli/reference)
- `codex exec` flags: `--json` "Print newline-delimited JSON events instead of formatted text"; `--output-schema` "JSON Schema file describing the expected final response shape. Codex validates tool output against it"; `-o/--output-last-message` "Write the assistant's final message to a file"; `--ephemeral` "Run without persisting session rollout files to disk"; `--approve-for-me` "automatic approval review with `on-request` approvals and the `workspace-write` sandbox"; `-m/--model`; `-c/--config` inline overrides (repeatable); `-C/--cd` workspace root. Exit codes 0 success / 1 error; `-` reads the prompt from stdin. — [Codex CLI reference](https://learn.chatgpt.com/docs/cli/reference); [mirror of exec docs](https://mintlify.wiki/openai/codex/cli/exec)
- **Sign in with ChatGPT, open-source token sharing**: "ChatGPT plan usage is an optional capability within Sign in with ChatGPT"; "This does not grant access to their ChatGPT conversations or other account context"; "These docs explain ChatGPT plan usage for open-source and locally hosted apps"; "If you're interested in offering it in a paid or remotely hosted app, complete the interest form"; before first sign-in "choose and persist the required `ext_agent_host_id`" (opaque; JWK-thumbprint URI, `urn:uuid:`, or `did:key:`); requests use `store: false` and `stream: true` against the Responses API with the bearer access token; "Configure Codex app-server to use an OAuth access token authorized for ChatGPT plan usage." Nothing in the doc mentions `~/.codex/auth.json`. — [OpenAI: SIWC token sharing for open source](https://developers.openai.com/siwc/token-sharing-open-source); [SIWC overview](https://developers.openai.com/siwc)
- Secondary: "the public API won't accept that [ChatGPT] token as a bearer key"; third-party tools reuse it "through a localhost proxy that mimics the Codex CLI request format"; OpenAI's Thibault Sottiaux "publicly endorsed using Codex subscriptions in third-party harnesses" (Feb 2026). — [SSD Nodes](https://www.ssdnodes.com/learn/codex-with-a-chatgpt-subscription); [Puter tutorial](https://developer.puter.com/tutorials/openai-oauth/); [The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/)
- OpenAI Terms of Use prohibit "automatically or programmatically extract[ing] data or Output"; an older (Dec 2023) version carved out "except as permitted through the API". The live terms page returned 403 to fetch; credential-sharing wording not verified. — [OpenAI Terms (EU/ROW)](https://openai.com/en-GB/policies/row-terms-of-use/); [commentary](https://ilikekillnerds.com/2023/11/15/openais-api-december-2023-terms-of-use-update/)
- OpenCode offers "ChatGPT Plus/Pro" OAuth for OpenAI in `/connect` and "recommends signing up for ChatGPT Plus or Pro"; credentials in `~/.local/share/opencode/auth.json`. — [OpenCode providers docs](https://opencode.ai/docs/providers/)
- Pi: `/login` offers "ChatGPT Plus/Pro (Codex)"; tokens in `~/.pi/agent/auth.json`, "auto-refresh when expired"; API keys via `OPENAI_API_KEY` or stored under the `openai` key. — [pi-coding-agent docs/providers.md](https://cdn.jsdelivr.net/npm/@earendil-works/pi-coding-agent@0.81.1/docs/providers.md)
- **Current OpenAI API models** (developers.openai.com models page, read 2026-10-21): flagship `gpt-6-astra` (1.05M ctx, "Most capable model, for complex reasoning and coding"), `gpt-6.1-sol` (1.05M, "Near-Astra performance … at lower cost"), `gpt-6-luna` (1.05M, "Most efficient model", supports reasoning effort `none`); specialized `gpt-5.6-cyber` etc. No dedicated `*-codex` model listed on that page. — [OpenAI models](https://developers.openai.com/api/docs/models)
- Codex-side model churn: GPT-5.5 retired from ChatGPT/Codex on 2026-10-14 with `gpt-5.6-sol` reported as the replacement for ChatGPT-authenticated Codex users; API unaffected. (Secondary.) — [letsdatascience](https://letsdatascience.com/news/openai-retires-gpt-55-from-chatgpt-and-codex-1a6f69be)

### Inferences
- OpenAI's posture is materially friendlier than Anthropic's: there is an official, documented program (SIWC + plan usage) for open-source/local tools to use a ChatGPT plan, and OpenAI leadership publicly endorsed third-party harness use. But that program is a *separate OAuth client registration*, not "read `~/.codex/auth.json`". Reading auth.json is undocumented, and the doc's own headless guidance (copying auth.json between *your* machines) is about the same user running Codex, not another product.
- Practical BYOK ladder for OpenAI: `OPENAI_API_KEY` env → user-pasted key → `codex exec --output-schema` subprocess (uses whatever Codex is logged in as, including ChatGPT plan) → (later) a registered SIWC client. Because Codex model names churn, let `codex` pick its default (plannotator passes no `-m` unless the user chose one).
- Model list for direct API use should be fetched from `GET /v1/models` rather than hardcoded; `gpt-6-luna` is the natural cheap default, `gpt-6.1-sol`/`gpt-6-astra` for quality.

### Gaps
- No OpenAI document found that states whether a third-party tool may read `~/.codex/auth.json`; treat as grey/unsanctioned. OpenAI Terms of Use could not be fetched (403); the credential-sharing clause is unverified.
- `auth.json` field names (`OPENAI_API_KEY`, `tokens.access_token/refresh_token/id_token/account_id`, `last_refresh`) are not in OpenAI docs; I did not verify from source in this pass (Codex not installed locally).
- The eligibility/approval process for SIWC open-source clients ("Request a client ID") was not read in detail.

## B3. How existing BYOK tools handle credentials (plannotator, opencode, pi, aider, avante/codecompanion, llm, mods, tuicr)

### Takeaway
Two clear camps: **subprocess tools** (plannotator) that never touch credentials and just require `claude`/`codex`/`opencode`/`pi`/`copilot`/`agent` on PATH; and **direct-API tools** that keep their own store (opencode `~/.local/share/opencode/auth.json`, pi `~/.pi/agent/auth.json`, llm `llm keys set`) or read `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` (aider, mods). ## B4. Recommended architecture: provider abstraction, model lists, streaming, prompt caching, token budgeting, and zero-config subprocess paths

### Takeaway
Build a two-tier provider layer: **CLI engines** (`claude -p`, `codex exec`) as the zero-config default that inherit the user's login and subscription, and **direct-API providers** (Anthropic SDK with `ANTHROPIC_API_KEY`/`ant auth` profile; OpenAI SDK with `OPENAI_API_KEY`) for users with keys. Use schema-enforced structured output on both CLIs (`--json-schema` / `--output-schema`), stream NDJSON for progress, put the (large, stable) diff *before* the (small, variable) instructions and cache it on the direct Anthropic path, and chunk big PRs per file-group with a two-pass "outline then fill" strategy rather than one giant call.

### Cited Findings
- **Claude CLI structured output**: `claude -p … --output-format json --json-schema '<schema>'` returns metadata plus `structured_output`; "If a run ends without valid structured output … the response has no `structured_output` field"; invalid schema → `Error: --json-schema is not a valid JSON Schema`; `format` keyword is annotation-only. Streaming: `--output-format stream-json --verbose --include-partial-messages`, last line is a `result` message; stdin capped at 10 MB ("write the content to a file and reference the file path" for larger); `--output-format json` includes `total_cost_usd`; `--bare` for hermetic runs (needs API key); `--setting-sources user` and `--strict-mcp-config` recommended when running in an untrusted repo (plannotator does this); permission: `--permission-mode dontAsk` + `--allowedTools`. — [Claude Code docs: Headless](https://code.claude.com/docs/en/headless.md); [plannotator claude-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/claude-review.ts)
- **Codex CLI structured output**: `codex exec --output-schema schema.json -o out.json --ephemeral` (+ `--json` for JSONL events); plannotator materializes the schema to a file in its data dir and passes `-m`/`-c model_reasoning_effort=…` *before* `exec`. — [Codex CLI reference](https://learn.chatgpt.com/docs/cli/reference); [plannotator guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)
- **Agent SDK vs subprocess**: "To drive the same agent loop from a language other than Python or TypeScript, run the CLI as a subprocess with the `-p` flag and `--output-format json`." — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- **Current Claude model IDs and prices** (bundled `claude-api` skill, cached 2026-10-06; "use only the exact model ID strings … never append date suffixes"): `claude-fable-5-1` (1M ctx, $10/$50 per MTok, thinking always on, effort `low…max`, 30-day retention required); `claude-opus-5-5` ($4/$20, default effort `medium`, thinking can't be disabled); `claude-sonnet-5-5` ($2/$10, default effort `high`); `claude-haiku-5-5` ($0.10/$0.50 up to 100K prompt tokens, $0.50/$2.50 beyond); older: `claude-opus-5`, `claude-opus-4-8`, `claude-opus-4-7`, `claude-opus-4-6`, `claude-sonnet-5`, `claude-sonnet-4-6`, `claude-haiku-4-5`. Live lookup via `GET /v1/models` (`max_input_tokens`, `max_tokens`, `capabilities`). Structured outputs: `output_config: {format: {...}}` (the old `output_format` is deprecated); forced `tool_choice` any/tool returns 400 on Fable 5.1/Opus 5.5/Sonnet 5.5; no assistant prefill on 4.6+; use streaming (`.stream()`/`get_final_message()`) for long outputs; `max_tokens` ~16k non-streaming / ~64k streaming defaults; `fallbacks: "default"` with beta `server-side-fallback-2026-07-01` recommended for refusal handling. — Claude Code bundled `claude-api` skill (SKILL.md, 2026-10-06 cache)
- **Prompt caching** (same skill): "Prefix match. Any byte change anywhere in the prefix invalidates everything after it. Render order is tools → system → messages. Keep stable content first … put volatile content … after the last `cache_control` breakpoint"; max 4 breakpoints; minimum cacheable prefix 512–4096 tokens depending on model; verify with `usage.cache_read_input_tokens`; Fable 5.1 cache reads $0.25/MTok, Opus 5.5 / Sonnet 5.5 $0.20/MTok; mid-conversation `{"role":"system"}` messages preserve the cached prefix on Opus 5 / 5.5 / Fable / Sonnet 5.5 / Haiku 5.5. — Claude Code bundled `claude-api` skill
- **Token counting**: use `POST /v1/messages/count_tokens` (`messages.count_tokens`), "never tiktoken". Long contexts: server-side compaction beta `compact-2026-01-12` (default trigger 150K tokens) and `task_budget` (beta `task-budgets-2026-03-13`, min 20,000). — Claude Code bundled `claude-api` skill
- **OpenAI models**: `gpt-6-astra`, `gpt-6.1-sol`, `gpt-6-luna` (1.05M context each; Luna supports reasoning effort `none`). — [OpenAI models](https://developers.openai.com/api/docs/models)
- **Plannotator's budgeting approach**: the guide prompt itself constrains cost ("Reading [the diff] once, carefully, is 90% of the job"; at most two intent reads; stop at the third exploratory tool call); per-file `summary` must be written "from the diff hunks you already have"; `--effort` passed through to Claude, `model_reasoning_effort` to Codex; repair jobs forced to `low`. — [plannotator guide-prompt.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-prompt.ts); [guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)
- Research support for chunking large PRs: reviewer attention dilutes ~8.7% per extra file and ~10-file PRs had the lowest latent-bug rate. — [arXiv 2609.22610](https://arxiv.org/abs/2609.22610)

### Inferences (architecture recommendations)
- **Provider trait**: `generateGuide(input: {diff, changedFiles[], hunks[], prMeta?, instructions?}, opts: {model?, effort?, onProgress}) → GuideOutput`, with implementations `ClaudeCli`, `CodexCli`, `AnthropicApi`, `OpenAiApi` (and later `OpenCodeCli`/`PiCli` via marker blocks). Detection order: explicit config → `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` env → `claude`/`codex` on PATH (and `claude`-reported login state) → prompt the user. Never read `~/.claude/.credentials.json`, the `Claude Code-credentials` keychain item, or `~/.codex/auth.json`.
- **Schema**: keep the output schema small and enforceable (plannotator's is ~40 lines); reference hunks by server-assigned IDs (`h0…hN`) in the model's output and resolve them to `{path, hunk header, line range, content hash}` anchors yourself. Validate coverage (every hunk exactly once) and drop fabricated refs; feed a "Changed hunks" index block in the user message just as plannotator feeds "Changed files (+a/-d)".
- **Streaming**: consume `stream-json` (Claude) / `--json` JSONL (Codex) only for progress UI; the authoritative payload is the final `structured_output` / `-o` file. Implement plannotator-style mechanical JSON repair and a cheap "repair" re-run at `low` effort.
- **Caching on the direct Anthropic path**: system prompt (methodology) first with a `cache_control` breakpoint, then the diff as the first user content block with a second breakpoint, then the hunk index and instructions. Re-runs (regenerate, repair, per-chunk deepening) then hit the cache for the diff. A Haiku 5.5 pre-pass to draft per-file summaries and an Opus 5.5 pass to chapter/order is a reasonable cost split; Fable 5.1 only when the user asks.
- **Big PR strategy**: (1) count tokens (`count_tokens`); if the diff plus overhead exceeds a budget (e.g. 150–200K), (2) pre-group hunks by file/directory and symbol overlap, (3) ask the model for an *outline* (chapters as sets of hunk IDs with one-line titles) using a hunk index plus truncated per-hunk previews instead of the full diff, then (4) fill each chapter's prose with only that chapter's hunks (cached methodology prefix). For the CLI engines, write the diff to a temp file and reference it in the prompt (stdin is capped at 10 MB on `claude -p`; Codex has `-C cwd` so it can run `git diff` itself).
- **Zero-config path**: ship `claude -p --bare?`—no: `--bare` disables subscription login, so for the subscription path use plannotator's exact flag set (`-p --permission-mode dontAsk --output-format stream-json --verbose --json-schema … --no-session-persistence --setting-sources user --strict-mcp-config` with a read-only `--allowedTools` list) and for Codex `codex exec --output-schema … -o … --ephemeral --approve-for-me -C <cwd>`.

### Gaps
- Current OpenAI per-token pricing and the Responses API structured-output parameter names were not fetched in this pass; verify before implementing the direct OpenAI provider.
- Whether `claude -p` launched by a third-party tool is treated as "third-party app usage" (subscription limits) vs. "Agent SDK/API credits" after Anthropic's 2026-10-07 update is not fully clear from the excerpts obtained; the support article should be re-read in full before documenting billing behaviour to users.
