# Build a Rust TUI, Lease Neovim for Depth

No existing tool occupies the cell this project targets: a terminal surface that reviews **local branch stacks before they are pushed**, pulls GitHub PRs into a **temporary worktree** so the whole codebase is navigable, generates a plannotator-style **guided walkthrough** with the user's own credentials, and offers **LSP jump-to-definition**. tuicr (Rust, 3,431 stars, MIT) has the comment, reviewed-mark and forge-push machinery but no AI, no LSP and no stack concept; plannotator (TypeScript, 9,556 stars) has the guide schema, worktree PR mode and GraphQL stack walk but is browser-based, file-level rather than hunk-level, and navigates with ripgrep ([tuicr](https://api.github.com/repos/agavra/tuicr); [plannotator](https://api.github.com/repos/backnotprop/plannotator)). The recommendation is to build a **standalone Rust engine plus ratatui TUI**, not a Neovim plugin, because roughly three quarters of the work (stack detection, worktree management, guide generation, provider/credential layer, review-state store, LSP client) is editor-independent, the Neovim-only advantages have shrunk now that **TypeScript 7.0 ships a native `tsc --lsp --stdio` server** that starts in about a second ([TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)), and the Neovim foundation the plugin would rest on is churning (diffview upstream dead since 2024, plenary end-of-life, nvim-treesitter rewritten and briefly reported archived). Neovim users still get the best of both through the lazygit pattern: when `$NVIM` is set the TUI opens files in the parent editor via `nvim --server --remote`, and a thin optional plugin can later render the same guide JSON as a markdown buffer with tree-sitter injections. Two constraints shape everything else: Anthropic's legal page now states developers "may not collect, store, or intermediate Claude.ai credentials or session tokens", so BYOK must mean either a user-supplied API key or spawning the unmodified `claude -p` binary, never reading the keychain ([Anthropic legal](https://code.claude.com/docs/en/legal-and-compliance)); and plannotator's own ADR found that local stack-parent detection has a child-branch trap that is "provably undetectable by graph queries alone", so local stacks must be suggested, never auto-applied, with the forge's declared PR base chain treated as truth once a PR exists ([plannotator ADR](https://github.com/backnotprop/plannotator/blob/main/adr/eval-local-stack-detection-20260703.md)).

## No tool today combines local stacks, hunk-level guides, BYOK and LSP

The survey covered roughly fifteen tools, and the empty cell is unambiguous. tuicr is the closest terminal peer: a single Rust/ratatui binary created in January 2026, now at v0.27.0 with roughly weekly releases, offering a continuous GitHub-style diff, line/range/file/review comments, **file- and hunk-granularity reviewed marks persisted as JSON sessions**, export to six forges, git/jj/Mercurial backends, and an agent-facing `tuicr review` JSON CLI that ships with a Claude Code skill ([tuicr README](https://github.com/agavra/tuicr/blob/main/README.md); [REVIEW_CLI](https://github.com/agavra/tuicr/blob/main/docs/REVIEW_CLI.md)). Its design ceiling is explicit in source: `pr_open.rs` states "The current local checkout is never treated as the source of truth" and "No checkout mutation. We never spawn `git checkout/fetch/reset/stash`", so PR review is forge-API diff only ([pr_open.rs](https://github.com/agavra/tuicr/blob/main/src/forge/pr_open.rs)). A grep for "stack", "lsp" or any model provider in its README, docs and `src/` returns nothing, and a third-party reviewer criticises that it "outputs all review comments in one go, without tying them to specific commits" ([jvt.me](https://www.jvt.me/posts/2026/08/25/tuicr/)). Those three absences, stacks, LSP and AI, are exactly this project's differentiators.

Plannotator is the design reference for the guide and PR mode but it is a different kind of product: "a local, browser-based review surface" served from a Bun process, with a separate `plannotator-tui` that reviews Markdown documents only, not code ([plannotator README](https://github.com/backnotprop/plannotator)). Its PR mode is worth copying closely. If the current repo matches the PR's host/owner/repo it fetches `refs/pull/<N>/head` into a **detached `git worktree`**; otherwise it runs `gh repo clone owner/repo <dest> -- --depth=1 --no-checkout`, and the checkout is deleted when the session ends ([pull-requests docs](https://docs.plannotator.ai/open-source/workflows/pull-requests.md); [pr-types.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-types.ts); [worktree.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/worktree.ts)). It marks a PR as stacked when `baseBranch !== defaultBranch` and walks the stack with GitHub GraphQL `pullRequests(headRefName:/baseRefName:)` queries, offering "Layer" (`origin/<base>...HEAD`) and "Full stack" (`origin/<default>...HEAD`) diff scopes ([pr-stack.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-stack.ts)). Its code navigation, however, is explicitly "Search-based" via `rg`, returning `likely`/`possible` confidence rather than LSP precision ([code-nav.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/code-nav.ts)), and "BYOK" means the installed agent CLI: engines are detected "by checking for their command on PATH" and "Plannotator does not create accounts or manage provider API keys" ([agent-reviews docs](https://docs.plannotator.ai/open-source/workflows/agent-reviews.md); [ask-ai docs](https://docs.plannotator.ai/open-source/workflows/ask-ai)).

The remaining peers each hold one piece. lumen is the only Rust TUI with BYOK AI (`lumen explain` with "10+ providers" on the user's own key) and GitHub-synced viewed state ([lumen](https://github.com/jnsahaj/lumen)); difit and revdiff are copy-to-agent exporters with file-level viewed marks, revdiff's surviving reload "only if diff unchanged" ([difit](https://github.com/yoshiko-pg/difit); [revdiff](https://revdiff.com/)); hunk shows agent-authored annotations only ([hunk](https://github.com/modem-dev/hunk)); octo.nvim is the mature GitHub-review Neovim plugin with range comments and `toggle_viewed` ([octo.nvim](https://github.com/pwntester/octo.nvim)); and the hosted reviewers (Claude Code Code Review, CodeRabbit, Bugbot, Greptile) produce "summary + walkthrough table + inline findings", never an ordered reading path ([CodeRabbit config](https://docs.coderabbit.ai/reference/configuration); [Claude Code review](https://code.claude.com/docs/en/code-review)). The only product besides plannotator that reorders a diff for reading is Amp's "Intelligently Ordered Diffs", which moves explanatory files to the top and mutes tests and fixtures, with "a blue dot" when the ordering updates, but with no prose ([Amp](https://ampcode.com/news/intelligently-ordered-diffs)).

Two implications follow. First, tuicr's session format (JSON files keyed by slugs like `gh:owner/repo/pr/N` and `owner/repo@branch/worktree`, with an `active_sessions.json` registry and a polling-based agent skill) is a de facto protocol for agent-to-reviewer handoff worth interoperating with rather than reinventing ([REVIEW_CLI](https://github.com/agavra/tuicr/blob/main/docs/REVIEW_CLI.md); [tuicr skill](https://github.com/agavra/tuicr/blob/main/skills/tuicr/SKILL.md)). Second, the academic literature backs hunk-level chunking and per-chunk coverage: untangling work from CLUSTERCHANGES through Flexeme (0.81 accuracy on C#) and SmartCommit (71 to 84 percent median accuracy) clusters by def-use dependencies between hunks ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/helping-developers-help-themselves-automatic-decomposition-of-code-review-changesets/); [Flexeme](https://2020.esec-fse.org/details/fse-2020-papers/27/Flexeme-Untangling-Commits-Using-Lexical-Flows); [SmartCommit](https://2021.esec-fse.org/details/fse-2021-papers/20/SmartCommit-A-Graph-Based-Interactive-Assistant-for-Activity-Oriented-Commits)), and a September 2026 study of 330,343 PRs found the latent bug rate rises from **56.7 percent at file position 1 to 61.5 percent at position 30** and each additional file cuts the odds of any review comment by about 8.7 percent, recommending "dependency-aware grouping" and "per-file coverage indicators" ([arXiv 2609.22610](https://arxiv.org/abs/2609.22610)).

## TypeScript 7's native LSP makes per-worktree navigation cheap

The single most consequential technical change for requirement (4) is that **TypeScript 7.0 went GA on July 8, 2026 with a built-in LSP server and without `tsserver.js`**. The announcement states "The new foundation is built on the Language Server Protocol (LSP) and is able to leverage multiple threads", that "Any editor with LSP support should work with TypeScript 7", and reports time-to-first-error on the VS Code codebase dropping from about 17.5 seconds to under 1.3 seconds and Canva from about 58 seconds to about 4.8 seconds ([TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). The launch form in practice is `tsc --lsp --stdio` (the preview name `tsgo` was retired when the staging repo was archived on September 1, 2026), and an `initialize` handshake advertises completion, hover, go-to-definition, references, code actions and rename ([typescript-go](https://github.com/microsoft/typescript-go); [arunmozhi.in](https://arunmozhi.in/2026/07/10/using-typescript-v7-with-emacs-eglot/)). The same community report explains why the old route broke: typescript-language-server fails with "Could not find a valid TypeScript installation" because "TypeScript 7 dropped the `tsserver.js` that the adapter depended on", and the typescript-language-server README now says TS 7's LSP "will hopefully supersede this project" ([typescript-language-server](https://github.com/typescript-language-server/typescript-language-server)). vtsls (wrapping VS Code's bundled TypeScript) and `ts_ls` remain the servers for TS 6 and earlier workspaces; vtsls has the better monorepo and `globalTsdk` story but makes no TS 7 statement ([vtsls](https://github.com/yioneko/vtsls)). The tool should therefore probe the worktree's TypeScript major version and pick `tsc --lsp --stdio` for 7+, vtsls or `typescript-language-server --stdio` otherwise.

Two gotchas carry over from any server. The client must send a real `rootUri`/`workspaceFolders` pointing at the worktree: a Claude Code bug report shows `rootUri: null` made typescript-language-server unable to find `tsconfig.json` or `node_modules/typescript`, crash, and return empty cross-file definitions ([claudeissues 31365](https://claudeissues.com/issue/31365-bug-lsp-tool-passes-rooturi-null-during-initialization-breaking-typescript-langu)). And a worktree without `node_modules` yields mass errors and broken definition into dependencies, since worktrees share the object store but not ignored artefacts; the standard mitigation is symlinking `node_modules` from the main checkout (the `git-worktree-share` approach), with an async `npm ci`/`pnpm install` as the fallback for pnpm, Yarn PnP or nested-package layouts where symlinks break ([git-worktree-share](https://github.com/keithamus/git-worktree-share); [geekcoderjournal](https://geekcoderjournal.substack.com/p/typescript-language-server-automatic?r=1c2kt)). No primary source tested tsserver against a symlinked `node_modules` in a worktree, so treat the symlink as a hypothesis to verify in week one.

On the client side, Rust has no shared "LSP client" crate: Helix hand-rolls JSON-RPC over stdio on tokio with a fork of `lsp-types` at 0.95.1, Zed does the same with `lsp-types` plus `futures`, and `async-lsp` 0.2.4 (tower-based, "can build both a language server and a language client") is the only general-purpose option, pinned to `lsp-types` 0.95 while crates.io's latest 0.97 has been stale since June 2024 ([helix-lsp](https://raw.githubusercontent.com/helix-editor/helix/master/helix-lsp/Cargo.toml); [zed lsp](https://raw.githubusercontent.com/zed-industries/zed/main/crates/lsp/Cargo.toml); [async-lsp](https://docs.rs/crate/async-lsp/latest); [lsp-types](https://crates.io/api/v1/crates/lsp-types)). The minimal client this tool needs is small: spawn, `initialize` with the worktree root, `initialized`, `textDocument/didOpen` for files the user navigates, `textDocument/definition` and `textDocument/hover`, `shutdown`/`exit`. The TS 7 startup numbers make "spawn one server per review worktree" viable in a TUI in a way it was not with multi-second tsserver boots. Note also that **TS 7.0 shipped without a programmatic API** (a new API is expected in 7.1), which blunts the classic argument for writing the tool in TypeScript so it could "just call the compiler API": even a TS app would talk LSP to `tsc --lsp` for TS 7 projects ([TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)).

In Neovim the LSP story is better and worse at once. Neovim 0.11+ `vim.lsp.config`/`vim.lsp.enable` resolves the root per buffer upward from the file via `root_markers` and reuses a client only when name and `root_dir` match, so a worktree under a cache directory gets its own client automatically ([:help vim.lsp.Config](https://neovim.io/doc/user/lsp.html#vim.lsp.Config)). But LSP attaches to a buffer with a real file URI and filetype; nothing in `lsp.txt` associates a sub-range of a prose buffer with another file, so "jump-to-definition from inside a guide excerpt" is not free in Neovim either. The realistic pattern is "excerpt as portal": a keymap on the excerpt opens the real worktree file at the mapped line and calls `vim.lsp.buf.definition()` or `hover()` there. That is structurally the same thing a standalone TUI does when it hands a file and line to `nvim --server $NVIM --remote` ([:help remote](https://neovim.io/doc/user/remote.html)).

## Anthropic bans credential intermediation, so BYOK means keys or the `claude` binary

The credential policy is the hardest external constraint and it moved repeatedly during 2026. Claude Code stores subscription OAuth in the macOS Keychain (observed item service `Claude Code-credentials`, account = OS user) or `~/.claude/.credentials.json` with mode 0600 on Linux and as macOS fallback, with precedence running cloud-provider credentials, then `ANTHROPIC_AUTH_TOKEN`, then `ANTHROPIC_API_KEY` ("In non-interactive mode (`-p`), the key is always used when present"), then `apiKeyHelper`, then `CLAUDE_CODE_OAUTH_TOKEN`, then the `ant auth login` profile, then subscription OAuth ([Claude Code authentication](https://code.claude.com/docs/en/authentication)). The field names in `.credentials.json` (`accessToken`, `refreshToken`, `expiresAt`) are community-reported only, and a GitHub issue documents headless copies failing with 401 after expiry instead of refreshing ([claude-code #50743](https://github.com/anthropics/claude-code/issues/50743)).

The policy text, verified verbatim on 2026-10-21, is explicit. "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." Developers "should use API key authentication", Anthropic "does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users", and "developers may not collect, store, or intermediate Claude.ai credentials or session tokens". The same page carves out the escape hatch: nothing "prevent[s] an end user from signing in to the unmodified Claude Code binary with their own Claude subscription", provided "The Claude Code binary must not be modified" and each user authenticates with their own credentials ([Anthropic legal](https://code.claude.com/docs/en/legal-and-compliance)). The Agent SDK overview repeats that "Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). Enforcement is real: in January 2026 Anthropic blocked third-party harnesses "spoofing the Claude Code harness", OpenCode removed Claude Pro/Max support citing legal requests, and OpenCode's docs today still say "Anthropic explicitly prohibits this" ([The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/); [OpenCode providers](https://opencode.ai/docs/providers/)). A May 2026 restriction and "Agent SDK credit" were later paused; the support article (updated 2026-06-15 and 2026-10-07) now says "You can still use the Claude Agent SDK, `claude -p`, and third-party apps with your subscription limits" and that Max and Team plans include monthly credits covering `claude -p` and the API ([support.claude.com](https://support.claude.com/en/articles/15036540); [VentureBeat](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch)). Whether a `claude -p` call launched by this tool bills to subscription limits or credits after October 7 is not fully clear from the article excerpts and should be re-read before documenting billing to users.

OpenAI's posture is friendlier but equally clear that the file on disk is not the interface. Codex caches credentials in `~/.codex/auth.json` or the OS keyring (`cli_auth_credentials_store = file|keyring|auto|ephemeral`), refreshes ChatGPT tokens automatically, and the docs say "Treat `auth.json` like a password" and "API keys are still the recommended default for automation" ([Codex authentication](https://learn.chatgpt.com/docs/auth)). The sanctioned route for a third-party local tool to use a ChatGPT plan is **Sign in with ChatGPT** with the opt-in "ChatGPT plan usage" capability, documented "for open-source and locally hosted apps", requiring a persisted `ext_agent_host_id` and `store: false`, `stream: true` requests against the Responses API; paid or hosted apps must apply via a form ([SIWC token sharing](https://developers.openai.com/siwc/token-sharing-open-source)). No OpenAI text was found that permits or forbids another tool reading `auth.json`; treat it as grey and avoid it. Secondary sources report the public API rejects the ChatGPT token as a bearer key, which is why some tools proxy through Codex-shaped requests, a pattern to avoid ([SSD Nodes](https://www.ssdnodes.com/learn/codex-with-a-chatgpt-subscription)).

The compliant BYOK design is therefore a two-tier provider layer, which is also what every surviving tool converged on. Plannotator never touches credentials: a repo grep for `ANTHROPIC_API_KEY|credentials.json|Keychain|auth.json|OPENAI_API_KEY` hits nothing in its review or guide engines, and it invokes `claude -p --permission-mode dontAsk --output-format stream-json --verbose --json-schema <schema> --no-session-persistence --setting-sources user --strict-mcp-config` with a read-only `--allowedTools` list, and `codex [-m model] exec --output-schema <file> -o <out> --approve-for-me --ephemeral -C <cwd>` with global flags before `exec` ([guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts); [claude-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/claude-review.ts)). The Agent SDK docs endorse exactly this for non-TS/Python hosts: "run the CLI as a subprocess with the `-p` flag and `--output-format json`" ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). Headless `claude -p` returns `structured_output` when the schema validates, caps stdin at 10 MB (write large diffs to a file and reference the path), and `--bare` is the hermetic mode that "never reads OAuth credentials or the system keychain", which means `--bare` is for the API-key path only, not the subscription path ([Claude Code headless](https://code.claude.com/docs/en/headless.md)). The direct-API tier reads `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` or an `ant auth` profile through the official SDK, and `OPENAI_API_KEY` through OpenAI's, fetching model lists from `/v1/models` rather than hardcoding (current Claude IDs include `claude-sonnet-5-5` at $2/$10 per MTok and `claude-haiku-5-5` at $0.10/$0.50; OpenAI's are `gpt-6-astra`, `gpt-6.1-sol` and `gpt-6-luna` at 1.05M context) ([OpenAI models](https://developers.openai.com/api/docs/models)). Detection order: explicit config, then API-key env vars, then `claude`/`codex` on PATH with the CLI itself asked for login state, then prompt the user. The tool must never read `~/.claude/.credentials.json`, the keychain item, or `~/.codex/auth.json`, and must not accept a pasted `CLAUDE_CODE_OAUTH_TOKEN` as a direct-API credential: that is "intermediating" a session token, it needs the undocumented `anthropic-beta: oauth-2025-04-20` header, and it is what got OpenCode blocked. On the API path, put the stable methodology system prompt and the large diff before the volatile instructions with `cache_control` breakpoints so regenerate, repair and per-chunk deepening hit the cache (prefix caching is byte-exact, max four breakpoints, cache reads at $0.20 to $0.25 per MTok on current models), and use `count_tokens` rather than a local tokenizer to decide when to switch to a two-pass "outline then fill" strategy for large PRs.

## Neovim rents rendering for free; Rust buys reach and a working template

The plugin route is genuinely feasible, and the user's own setup (Neovim 0.12.4, orgmode, render-markdown, mini.diff, nvim-lspconfig, `typescript-language-server` and `gh` on PATH) removes most onboarding friction for one user. Neovim 0.12 bundles the markdown parser with highlighting on by default, and the shipped injection query `(fenced_code_block (info_string (language) @injection.language) (code_fence_content) @injection.content)` means a guide document written as a markdown scratch buffer gets per-language syntax inside fenced blocks with zero code ([markdown injections.scm](https://github.com/neovim/neovim/blob/master/runtime/queries/markdown/injections.scm); [:help treesitter-language-injections](https://neovim.io/doc/user/treesitter.html#treesitter-language-injections)). Diff colouring layers on top deterministically because `vim.hl.priorities` fixes syntax at 50, treesitter at 100 and user extmarks at 200, so a background-only `DiffAdd` `line_hl_group` extmark sits under injected foreground colours with no tricks ([:help vim.hl.priorities](https://neovim.io/doc/user/lua.html#vim.hl.priorities); [:help nvim_buf_set_extmark](https://neovim.io/doc/user/api.html#nvim_buf_set_extmark())). nvim-orgmode proves the org-babel-style rendering the user described works on 0.12 via a custom `#org-set-block-language!` injection directive ([orgmode injections](https://raw.githubusercontent.com/nvim-orgmode/orgmode/master/queries/org/injections.scm)), and `vim.text.diff()` (renamed from `vim.diff()` in 0.12) plus extmarks is the unified-diff pattern used by mini.diff, unified.nvim and codediff.nvim ([:help vim.text.diff](https://neovim.io/doc/user/lua.html#vim.text.diff()); [mini.diff](https://github.com/nvim-mini/mini.diff)). dimfeld's diffview fork is direct prior art for persistent reviewed marks, storing per-branch blob hash and timestamp so marks "persist even if commit hashes change", with Unreviewed/Reviewed/Changed states and a "since-review" diff mode ([dimfeld/diffview.nvim](https://github.com/dimfeld/diffview.nvim)).

The costs are structural rather than cosmetic. Reach is Neovim-only, and the review surface would depend on the user having TypeScript/TSX parsers installed, since only seven parsers ship with 0.12 and the rest come from nvim-treesitter. That project rewrote its `main` branch in March 2026 to require Neovim 0.12 "from scratch", was widely reported archived on April 3 (the GitHub API shows it un-archived and pushed on 2026-10-19), and Neovim core opened issue #39006 to upstream a "data-only" parser repo precisely because of this instability ([nvim-treesitter](https://github.com/nvim-treesitter/nvim-treesitter); [neovim#39006](https://github.com/neovim/neovim/issues/39006); [byteiota](https://byteiota.com/nvim-treesitter-archived-13k-star-plugin-shut-down-2026/)). The two-window diff host, sindrets/diffview.nvim, has not been pushed since **2024-08-02** and lives on only as the diffview-plus fork at 360 stars ([diffview-plus](https://github.com/dlyongemallo/diffview.nvim)); plenary, which octo, codecompanion and typescript-tools depend on, is treated as end-of-life (avante's TODO reads "Get rid of archived plenary.nvim") ([avante](https://github.com/yetone/avante.nvim)). Async HTTP from Lua means shelling out to `curl` with `--no-buffer` as codecompanion does, because 0.12's `vim.net.request()` is GET-only ([codecompanion http.lua](https://raw.githubusercontent.com/olimorris/codecompanion.nvim/main/lua/codecompanion/http.lua); [:help vim.net.request](https://neovim.io/doc/user/lua.html#vim.net.request())). And the agent-handoff story, which tuicr shows is central to how these tools get used in 2026, requires a headless CLI surface that a plugin can only offer through `nvim --headless` gymnastics. Classic Vim is not a target at all: Vim 9.2 (February 2026) has no built-in LSP, tree-sitter, extmarks or Lua, and none of the Lua code would carry over ([helpnetsecurity](https://www.helpnetsecurity.com/2026/02/16/vim-9-2-released/)).

The standalone Rust route has a complete parts list and a working template. ratatui 0.30.2 (June 2026) with crossterm 0.29, edtui 0.11.7 (updated August 2026, tuicr's comment editor), tui-markdown 0.3.12 (updated October 2026) for prose, syntect 5.3 plus two-face for highlighting, imara-diff or similar for diffing, and git2 0.21 for git are all current ([ratatui releases](https://github.com/ratatui/ratatui/releases); [edtui](https://crates.io/api/v1/crates/edtui); [tui-markdown](https://crates.io/api/v1/crates/tui-markdown); [syntect](https://crates.io/api/v1/crates/syntect); [git2](https://crates.io/api/v1/crates/git2)). tuicr's Cargo.toml is effectively a bill of materials for the diff/comment/session layer, and it exposes a `ReviewStore` library API ([tuicr Cargo.toml](https://github.com/agavra/tuicr/blob/main/Cargo.toml)). The two things Rust must hand-roll are the mixed prose-plus-hunk document renderer (no crate renders markdown with embedded diff hunks; tui-markdown has no hook to inject pre-styled blocks) and the LSP client, both bounded. Distribution is essentially free: cargo-dist 0.33.0 (September 2026) generates shell and PowerShell installers, a Homebrew formula and an npm wrapper from one config ([cargo-dist releases](https://github.com/axodotdev/cargo-dist/releases)). The alternatives are real but weaker fits. Go's Charm stack reached v2 on 2026-02-23 and powers lazygit, gh-dash and crush, but offers no better rendering primitives than Rust ([charm.land v2](https://charm.land/blog/v2/)). TypeScript on OpenTUI has the most batteries, including built-in tree-sitter `CodeRenderable` with an `onHighlight` hook and a `MarkdownRenderable`, and is proven by OpenCode "for millions of users", but `bun build --compile` binaries weigh 60 to 150 MB plus native Zig platform packages ([OpenTUI](https://opentui.com/docs/components/code); [bun executables](https://bun.com/docs/bundler/executables.md)). The TS route's one unique asset is that plannotator's MIT/Apache guide packages (`packages/core/guide.ts`, `guide-prompt.ts`) could be imported verbatim; the Rust route gets the same value by porting a 40-line schema and a prompt.

| Criterion | Neovim plugin (Lua) | Standalone Rust TUI | TS/Bun OpenTUI |
|---|---|---|---|
| Prose + highlighted excerpts | Free (markdown injections + extmarks) | Hand-rolled two-layer `Span` styling; tuicr proves it | Built-in Code/Markdown renderables |
| Jump-to-def in excerpt | Portal to real buffer, user's LSP config | Own LSP client to `tsc --lsp`; `nvim --remote` handoff for editor users | Own LSP client |
| Stack/worktree/AI/state engine | Lua + `vim.system` + curl | Native, async, testable | Native |
| Agent handoff (JSON CLI, tmux pane) | Awkward (`--headless`) | tuicr-style CLI | Easy |
| Reach | Neovim users with parsers installed | Anyone with a terminal | Anyone; heavy install |
| Foundation risk | nvim-treesitter churn, plenary EOL, diffview fork | Mature crates; lsp-types stale but workable | OpenTUI young (0.6.6) |
| Template to copy | dimfeld fork, octo, mini.diff | tuicr (MIT) | plannotator packages |

The decision rests on where the irreducible work is. Requirements (1), (2), (3) and (6) are an engine: parsing diffs into a hunk model, detecting stacks, fetching `refs/pull/N/head`, creating and cleaning worktrees, symlinking `node_modules`, spawning `claude -p`/`codex exec` or calling APIs with cached prefixes, validating a guide schema, and persisting hash-keyed reviewed state. None of that wants to live in Lua. Requirement (4) tilted toward Neovim a year ago; with a native, sub-second TypeScript LSP it is a weekend of JSON-RPC in Rust. Requirement (5) is the only one Neovim wins outright, and the lazygit `--remote` pattern plus an optional thin plugin recovers most of it for Neovim users without making the project Neovim-shaped. The one option that deserves a conscious no is forking tuicr: it already has comments, reviewed hunks, sessions and six-forge export under MIT, but its invariants ("never treated as the source of truth", "no checkout mutation") are the opposite of a worktree-first design, and it ships roughly weekly, so a fork would carry a permanent merge tax. Borrow its code and its session slug format; do not inherit its architecture.

## Data contracts: hunk-anchored guide schema and conservative stack detection

### The guide schema should reference hunks by server-assigned ID, not line numbers

Plannotator's shipped guide is deliberately file-level. Its types are `GuideDiffRef { file; summary? }`, `GuideSection { title; overview; diffs[] }` and `CodeGuideOutput { title; intent; sections; unplacedFiles? }`, with the comment that "Semantic order ... is carried by the array position, not by any label field" ([guide.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide.ts)). The v1 spec originally had `lineStart`/`lineEnd`/`note` hints and a `kind: core|consequence|support` label and dropped both, listing "hunk-level slicing" as out of scope ([spec](https://github.com/backnotprop/plannotator/blob/main/adr/specs/guided-review-20260702-195351.md)). The parts worth copying unchanged are the prompt's chunking rule ("A section is a logical unit of change, not a file and not a folder. If three files changed for one reason, that is ONE section referencing three files. If one file has two unrelated changes, split it into two sections"), the ordering rule (implementation heart first, consequences next, one trailing glue chapter), the size bound ("Typically 2-6 sections. Never more than 10"), the research budget ("If you catch yourself on a third exploratory tool call, stop"), and above all the **fail-closed coverage rule**: "Every changed file must appear in EXACTLY ONE place", enforced server-side against the launch-time changed-file snapshot, with fabricated paths discarded and zero sections failing the job ([guide-prompt.ts](https://github.com/backnotprop/plannotator/blob/main/packages/core/guide-prompt.ts); [guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)). Plannotator's sibling Code Tour job already uses line-anchored `TourDiffAnchor` stops, showing the same team accepted finer anchors where the narrative needed them ([tour.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/tour.ts)).

To get hunk granularity without hallucinated ranges, the engine assigns every parsed hunk a stable index (`h0..hN`), feeds a "Changed hunks" block (path, hunk header, one-line preview) into the user message the way plannotator feeds "Changed files (+a/-d)", and the model references hunks only by those IDs. The engine resolves IDs to anchors itself. Reviewed-state semantics copy GitHub's, which is the industry norm: GitHub's GraphQL `FileViewedState` is `VIEWED`, `UNVIEWED` or `DISMISSED` ("The file has new changes since last viewed"), keyed per viewer by path ([GitHub GraphQL enums](https://docs.github.com/en/graphql/reference/enums); [GitHub docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)); Gerrit scopes the flag to (change, revision, file, account) ([Gerrit REST](https://gerrit-review.googlesource.com/Documentation/rest-api-changes.html)); Reviewable counts a file done only when "marked reviewed at the most recent revision" ([Reviewable](https://docs.reviewable.io/reviews.html)). None anchors below the file, so the hunk anchor is this project's own contribution.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "GuideOutput (model-facing)",
  "type": "object",
  "additionalProperties": false,
  "required": ["title", "intent", "chunks", "unplacedHunks"],
  "properties": {
    "title": { "type": "string" },
    "intent": { "type": "string", "description": "2-4 sentences: what the change does and why" },
    "chunks": {
      "type": "array", "minItems": 1, "maxItems": 10,
      "items": {
        "type": "object", "additionalProperties": false,
        "required": ["title", "overview", "hunks"],
        "properties": {
          "title": { "type": "string" },
          "overview": { "type": "string", "description": "markdown, 2-6 sentences; may use > [!IMPORTANT] / > [!WARNING]" },
          "role": { "enum": ["core", "consequence", "support"] },
          "risk": { "enum": ["low", "medium", "high"] },
          "hunks": {
            "type": "array", "minItems": 1,
            "items": {
              "type": "object", "additionalProperties": false,
              "required": ["id"],
              "properties": {
                "id": { "type": "string", "pattern": "^h[0-9]+$" },
                "note": { "type": "string", "description": "1-2 sentences written from the hunk only" }
              }
            }
          }
        }
      }
    },
    "unplacedHunks": { "type": "array", "items": { "type": "string", "pattern": "^h[0-9]+$" } }
  }
}
```

The persisted guide wraps that output with engine-resolved anchors and state, which the model never sees:

```json
{
  "kind": "revuey-guide", "version": 1,
  "source": { "kind": "local-stack|pr|range", "repo": "...", "baseSha": "...", "headSha": "...",
              "stack": [{ "branch": "feat/a", "pr": 123 }, { "branch": "feat/b", "pr": 124 }] },
  "generator": { "engine": "claude-cli|codex-cli|anthropic-api|openai-api", "model": "...", "generatedAt": "..." },
  "guide": { "...": "GuideOutput as above" },
  "anchors": {
    "h12": { "path": "src/auth.ts", "oldPath": null,
             "hunk": { "oldStart": 40, "oldLines": 6, "newStart": 40, "newLines": 9 },
             "newRange": [40, 48],
             "contentHash": "sha256(normalised hunk body)",
             "blobHash": "git blob sha of new side" }
  },
  "chunkIds": { "0": "sha256(sorted contentHashes of chunk 0's hunks)" },
  "reviewed": {
    "<chunkId>": { "state": "viewed|dismissed", "at": "...", "anchorHashes": ["..."] }
  },
  "files": { "src/auth.ts": { "state": "viewed|dismissed|unviewed", "blobHash": "...", "at": "..." } }
}
```

Three invariants make this robust. Resolution at render time is tiered: an exact `contentHash` match renders fresh; same path with an overlapping `newRange` but different hash renders as "changed since reviewed" and flips the chunk to `dismissed`, mirroring GitHub; a missing path renders plannotator's "outdated" chip. Coverage is validated by the engine against the parsed diff (every hunk exactly once across `chunks` and `unplacedHunks`, duplicates keep first placement, unknown IDs are dropped), with a trailing synthetic "Everything else" chunk for `unplacedHunks`. Chunk identity is derived from the sorted set of hunk content hashes rather than from the title, so a regeneration that reproduces the same grouping inherits reviewed state, and chunks whose anchor set changed get new IDs or carry state across on Jaccard overlap of at least 0.5. Keep `baseSha`/`headSha` so a whole-guide "Diff changed" banner costs one comparison, and follow Amp's pattern of regenerating in the background and offering to swap rather than discarding progress ([Amp](https://ampcode.com/news/intelligently-ordered-diffs)). Mechanical JSON repair (strip fences, slice first `{` to last `}`, strip trailing commas, close brackets) plus a low-effort "fix only syntax" re-run should ship from day one; plannotator needed all three ([guide-review.ts](https://github.com/backnotprop/plannotator/blob/main/packages/server/guide/guide-review.ts)). File-level reviewed state lives in the same store keyed by blob hash, as dimfeld's fork does, so it survives rebases ([dimfeld/diffview.nvim](https://github.com/dimfeld/diffview.nvim)). The state file belongs under the OS data directory (tuicr uses `~/Library/Application Support/tuicr/reviews` on macOS), keyed by a tuicr-compatible slug, never inside the repo's `.git` ([REVIEW_CLI](https://github.com/agavra/tuicr/blob/main/docs/REVIEW_CLI.md)).

For rendering, plannotator's ADR 007 is the right principle, "One renderer, two hosts": the guide mounts the same diff viewer per reference behind a `readOnly` flag, and a separate lean renderer was rejected because it "would drift on the first Pierre upgrade" ([ADR 007](https://github.com/backnotprop/plannotator/blob/main/adr/decisions/007-portable-guided-reviews-20260815.md)). In ratatui that means one `DiffFile`/`Hunk` model, one `render_hunk(hunk, highlight_range, annotations) -> Vec<Line>` that layers syntect foreground spans under diff background spans (the two-layer styling tuicr and gitui already do), and a guide view that is a flat virtualised list of `Prose(markdown)` and `HunkRef(id)` blocks with a side index mapping document lines back to (path, line) for jump-to-definition. Guide excerpts are references into the parsed diff, never copied text, so comments, viewed state and highlighting share one source of truth. Highlight each file once over its post-image so multi-line constructs are correct, then slice the hunk's lines.

### Stack detection: trust the forge, suggest locally, parse tool metadata when present

For GitHub PRs the universal fallback is plannotator's: a PR is stacked when `baseRefName !== defaultBranch`, and the stack is discovered by walking `baseRefName` upward to the default branch and `headRefName` downward to leaf PRs with GraphQL `pullRequests(headRefName:/baseRefName:, states:[OPEN, MERGED])` ([pr-stack.ts](https://github.com/backnotprop/plannotator/blob/main/packages/shared/pr-stack.ts)). This works because nearly every stacking tool sets each PR's base to the parent's head branch: Graphite PRs carry "This stack of pull requests is managed by Graphite" and base on the parent ([Graphite intro](https://graphite.com/docs/intro-to-graphite.md)); ghstack opens each PR against its own `gh/<user>/<N>/base` branch ([ghstack](https://github.com/ezyang/ghstack)); getcord/spr's `spr diff --all` creates PRs "stacked on top of each other" with `Pull-request:` trailers ([getcord/spr](https://github.com/getcord/spr)); GitButler targets "the nearest lower branch with a PR" ([GitButler](https://docs.gitbutler.com/features/stacked-branches)); Sapling appends a reviewstack.dev footer ([ReviewStack](https://sapling-scm.com/docs/addons/reviewstack/)). Fetch each layer with `git fetch origin pull/N/head:<ref>` into the user's existing clone (the `refs/pull/` namespace is read-only and touches no local branches) and create `git worktree add --detach` checkouts from the fetched SHAs ([GitHub docs](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally)); fall back to `gh repo clone --depth=1 --no-checkout` or a `--filter=blob:none` clone only when the current directory is not that repo. Shell out to `git` for clone, fetch and worktree: gitoxide's own status page lists checkout orchestration, worktree remove, partial clone, FETCH_HEAD and push as missing, and every surveyed Rust git TUI (tuicr, gitui, gitu) uses git2 for write paths ([gitoxide crate-status](https://raw.githubusercontent.com/GitoxideLabs/gitoxide/main/crate-status.md)). Offer "Layer" and "Full stack" scopes exactly as plannotator does, and only allow posting inline comments in Layer scope, since forge comments must map to that PR's diff ([pull-requests docs](https://docs.plannotator.ai/open-source/workflows/pull-requests.md)).

For unpushed local stacks, the heuristic ladder is: first read tool metadata that encodes intent, then infer, then ask. Graphite stores parent links as JSON blobs under `refs/branch-metadata/<branch>` in the object DB, readable without `gt` as `git-workon-lib` does ([Graphite blog](https://graphite.dev/blog/git-key-value); [git-workon-lib](https://docs.rs/git-workon-lib/0.11.1/src/workon/stack.rs.html)); jj exposes the stack as `jj log -r 'trunk()..@'` with change IDs stable across rebases ([jj-stack](https://www.serpentine.com/software/jj-stack/reference/bookmarks-and-selection/)); git-town keeps `git-town[-branch].<b>.parent` in git config; GitButler is detected by HEAD at `gitbutler/workspace` plus `gitbutler.project.targetref`; branch-name conventions (`gh/<user>/<N>/head`, `spr/*`, `push-<changeid>`, `sapling-pr-archive-*`) and trailers (`Pull-request:`, `ghstack-source-id:`, `commit-id:`) are cheap secondary signals. Absent metadata, use the merge-base reachability test plannotator evaluated: parent P qualifies for branch B when `merge-base(B,P)` is not an ancestor of trunk, choosing the deepest merge-base. That ADR passed clean cases but found a "dangerous" child-branch trap, where a branch cut from B wins and silently hides B's own commits, which is "provably undetectable by graph queries alone" because reflogs record only "Created from HEAD". Its determination is the right policy here: "Suggest, never auto-apply", show all qualifying parents, persist the user's explicit base choice per repo and branch as a ref name, and let the platform-declared base supersede once a PR exists ([plannotator ADR](https://github.com/backnotprop/plannotator/blob/main/adr/eval-local-stack-detection-20260703.md)). The pre-push review therefore shows the stack as an ordered list of layers (each with its own diff, comments anchored to the layer's commits, and reviewed state), which also fixes the commit-attribution gap reviewers complained about in tuicr.

## Recommended architecture and phasing

Structure the project as a Cargo workspace with an editor-agnostic `revuey-core` crate and thin hosts, mirroring how gitui separates `asyncgit` and yazi splits into ~24 crates. The core owns the diff model (parse `git diff` output or compute with imara-diff), the stack resolver, the worktree manager (fetch, `worktree add --detach`, `node_modules` symlink, cleanup on exit with a registry so crashes do not leak worktrees), the review store (JSON under the data dir, tuicr-compatible slugs, blob- and hunk-hash keys), the guide schema with validator and repair, the provider layer (`ClaudeCli`, `CodexCli`, `AnthropicApi`, `OpenAiApi` behind one `generate_guide`/`ask` trait), the LSP client (`async-lsp` or a Helix-style hand-rolled transport, `tsc --lsp --stdio` first, vtsls/ts_ls fallback), and the forge client (`gh api` and `gh auth token` for GitHub, honouring `GH_TOKEN`). Background work (git, LSP, model streaming) runs on a tokio runtime or dedicated threads feeding the ratatui loop through channels, the pattern gitui and yazi use ([gitui Cargo.toml](https://raw.githubusercontent.com/gitui-org/gitui/master/Cargo.toml)). A `revuey` CLI exposes the same JSON surface as tuicr's `review` subcommand (list sessions, add and read comments, dump the guide) so agents can drive it from a tmux pane, and the TUI is one client of that core.

Phase 0 (foundation, roughly two to three weeks) builds the core crate with the diff model, unified rendering with syntect, line/range/file comments in edtui, file- and hunk-level reviewed marks persisted by hash, and local stack resolution with the suggest-only parent heuristic; the deliverable is `revuey` on a local branch or stack, with clipboard/stdout export in tuicr's markdown shape. Phase 1 adds PR mode: GraphQL stack walk, `refs/pull/N/head` fetch, detached worktrees with `node_modules` symlink or install, Layer/Full-stack scopes, GitHub viewed-state sync via `markFileAsViewed`, and `gh`-based review posting. Phase 2 adds the guide and Ask AI through the CLI engines only (`claude -p --json-schema`, `codex exec --output-schema`), with the hunk-ID schema, validator, repair, chunk reviewed state and the one-renderer guide view; direct API providers with prompt caching, `count_tokens` budgeting and the outline-then-fill path for big PRs follow in Phase 3 once the CLI path has proven the schema. Phase 4 adds LSP: version-probe the worktree, spawn the server with a real `rootUri`, `gd` on any rendered line (main diff or guide excerpt) resolves through the side index to definition and opens the target file in a read-only pane, `K` renders hover markdown with tui-markdown, and `e` hands off to the editor through lazygit-style templates, using `nvim --server $NVIM --remote` plus `:{{line}}<CR>` when launched from Neovim's terminal ([lazygit editor presets](https://raw.githubusercontent.com/jesseduffield/lazygit/master/pkg/config/editor_presets.go)). Phase 5, optional and gated on demand, is a small Neovim plugin that reads the same guide JSON and state file and renders the guide as a markdown buffer with fenced blocks tagged by language (or `@injection.filename` so `vim.filetype.match()` handles `.tsx`), diff backgrounds as priority-200 extmarks, removed lines as `virt_lines`, and the portal keymap into the worktree file for the user's own LSP; because the state format is shared, marks made in either host appear in the other. Distribution through cargo-dist from Phase 0 gives Homebrew, shell installer and npm wrapper at no extra cost.

The risks to retire early are concrete. Verify in week one that `tsc --lsp` resolves definitions through a symlinked `node_modules` in a worktree; no primary source confirms it. Measure syntect cold-start with two-face's extended syntax set against the perceived launch time, since no benchmark exists. Re-read Anthropic's support article in full before documenting whether tool-launched `claude -p` bills to subscription limits or credits. And pin `lsp-types` deliberately: `async-lsp` wants 0.95 and the crate has not moved since 2024, so expect to vendor or fork as Helix did.

## Conclusion

The landscape has split into two camps that this project can bridge: terminal tools that treat the diff as text to annotate and export (tuicr, revdiff, difit) and browser or hosted tools that treat the change as something to be explained (plannotator, Amp, the hosted reviewers). The bridge is possible now for a reason that did not exist a year ago: TypeScript's native LSP collapsed the cost of semantic navigation in a worktree to a subprocess and a JSON-RPC loop, which removes the strongest argument for living inside an editor. The second-order insight from plannotator's own history is that the guide's value comes from invariants, not from the model: a tiny schema, server-assigned hunk IDs, fail-closed coverage validation and hash-derived identity do more for trust than any prompt engineering, and they are what let reviewed state survive regeneration and force-pushes.

Two things to hold onto as the build proceeds. The credential boundary is not a UX detail but a product constraint that has already killed features in OpenCode and others; designing the provider layer around "keys or the vendor's own binary" from the first commit avoids a rewrite under legal pressure later. And the stack-parent trap is a reminder that the pre-push review's correctness depends on an explicit, persisted user choice rather than cleverness in the graph walk; the tool that gets this right will be the first one reviewers can trust on a four-layer stack before any PR exists.
